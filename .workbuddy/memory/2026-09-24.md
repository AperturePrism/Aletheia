### 交付形态定案（用户核心问题：WebUI 还是多平台载体？）

**结论：自托管本地服务（daemon）+ WebUI 为主界面 + CLI 为控制平面 + MCP 为集成接口。明确不做桌面 GUI / 移动 App / 浏览器扩展。**

| 载体 | 定位 |
|---|---|
| `alethd` | 核心服务，单二进制（前端资源 embed 进二进制，用户下载一个文件即得完整系统含 UI） |
| **WebUI** | **主界面** —— React + Vite，不做 SSR |
| `aleth` | 控制平面（启动停止 / 脚本化 / CI / 状态查询），**不做交互式渗透主界面** |
| MCP | 双向集成（消费外部工具 / 被外部 agent 调用） |

**决策的关键论据（必须记住）**：本项目三个差异化能力**在结构上无法用 CLI 表达** ——
1. **证据链**：finding → assertions → evidence → exec_id → 原始输出行号，是多级树 + 交叉引用
2. **光圈上下文投影**：装了哪些实体 / 省略了哪些维度 / 为什么（selection_reasons）
3. **冲突矩阵**：三路观测的 4 象限，**"打不通但有缺陷"这个最高价值象限在 CLI 列表里会被淹没**

→ **若只有 CLI，这三个能力用户感知不到，项目退化成普通 CLI 渗透 agent，而这个赛道已有 PentestGPT / Strix 等成熟产品。**

**反面教材：HexStrike AI 把 UI 外包给第三方 MCP 客户端** → 实测客户端挂死、参数错误。因为 MCP 客户端不知道 Aletheia 的领域概念，无法为证据链/光圈/冲突矩阵设计界面。

**移动端明确不做**：操作性质不匹配（触屏不适合高信息密度任务）；CAI 的 iOS 端是 €350/月 PRO 的增值功能而非技术必需。替代方案 = WebUI 响应式适配（手机上能看进度、批准决策即可）。

**部署双模式同代码库**：单机（SQLite，默认仅监听 127.0.0.1）/ 团队（PostgreSQL + 多用户 + 远程 worker + 强制 TLS），配置切换。

### 2. 新增 `docs/schemas/roe.schema.json`

### 核心问题与应对

没有外部评审后，如何防止跑偏？**答案是：把评审职能内化为自检，且必须机械化。**

自检的固有缺陷是"自己给自己打高分"—— 这不是态度问题，是结构问题。因此 `10` 做了如下改造（v1 → v2）：

| 改造点 | 内容 |
|---|---|
| **新增 §0「自检的固有困难」** | 明确三种失真：**记忆替代验证**（记得写了≠代码里有）/ **绿灯替代有效**（测试绿了≠断言有效）/ **相似替代一致**（看起来符合≠真的符合） |
| **铁律改写** | 从"只信证据，不信自述" → **"只信证据，不信记忆"**。自检场景下"自述"就是自己的记忆 |
| **三条硬要求** | ① 每检查项须对应**可执行命令** ② 结论须附**原始输出**（不是复述"通过了"）③ 无法命令验证的须显式标注"仅人工判断"，且这类项越少越好 |
| **新增 §8「把检查固化为 CI」** | 核心洞察：**本文件的长期目标是让自己变得不必要**。判断标准：**连续两个迭代都靠人工完成的检查项，就该写成 CI 门禁** |
