# Aletheia — 交付形态与交互载体

> 版本：v1（决策稿）｜ 日期：2026-09-24
> 团队：**AperturePrism** ｜ 项目：**Aletheia**
> 上游依据：`02-架构设计文档.md` §1.3、§3、§7

## 0. 决策摘要

### 0.1 一句话结论

**Aletheia 是一个自托管的本地服务（daemon），以 WebUI 为主界面，CLI 为控制平面，MCP 为集成接口。**

### 0.2 载体决议表

| 载体 | 名称 | 定位 | 优先级 | 交付迭代 |
|---|---|---|---|---|
| **守护进程** | `alethd` | 核心服务，承载全部业务逻辑与 API | P0 | I0 |
| **WebUI** | — | **主界面** —— 任务编排、实时观测、证据浏览、人机协同决策、报告 | **P0（骨架）/ P1–P2（核心视图）** | see §10 |
| **CLI** | `aleth` | 控制平面 —— 启动停止、脚本化、CI 集成、状态查询 | P0 | I0 |
| **MCP 接口** | — | 集成 —— 双向（消费外部工具 / 被外部 agent 调用） | P2 | I11 |

### 0.3 明确不做的载体

| 载体 | 决议 | 理由摘要 |
|---|---|---|
| 桌面 GUI（Electron / Tauri） | **不做** | 本地服务 + 浏览器已完全覆盖；包体与维护成本不划算 |
| 移动 App（iOS / Android） | **不做**（v1.0 与 v2.0 均不做） | 渗透操作不适合触屏；CAI 的移动端属 PRO 增值的"陪伴式监控"，非核心 |
| 浏览器扩展 | **不做** | 与主界面功能重叠，且增加攻击面 |
| 第三方客户端托管 UI | **不做**（即不采用 HexStrike 路线） | 实测表明体验不可控（客户端挂死、无状态可视化） |

## 1. 为什么必须先定这个决策

在本文档之前，`02-架构设计文档.md` 的项目结构中同时存在 `web/` 目录与 CLI 入口，但**没有说明谁是主界面**。这会直接导致三个问题：

| 问题 | 后果 |
|---|---|
| 开发资源分散 | UI 与 CLI 各做一半，两个都不好用 |
| 交互设计缺位 | 核心能力（证据链、光圈投影、冲突矩阵）没有承载界面 |
| 范围蔓延 | 后续不断有人问"要不要做个桌面端""要不要上手机"，反复消耗决策成本 |

**本文档的作用是把这个决策一次性定死，并给出可辩护的理由。**

## 2. 决策依据

### 2.1 真实使用场景分析

四个场景，每个场景对载体的要求不同：

| 场景 | 使用者 | 需求 | 对载体的要求 |
|---|---|---|---|
| **A · 长时自主运行** | 研究者 / 红队 | 任务跑数小时到数天（对齐 AIxCC 的 143h 赛制）；需要随时查看进展；**需要断线重连** | **服务端持久化状态 + 浏览器界面**。CLI 的终端会话一断，上下文全丢 |
| **B · 人机协同决策点介入** | 红队 / 学生 | 调研结论：全自主 21% vs 有人类提示 64%。人类必须在高价值决策点介入（利用链方向、业务逻辑判断） | **需要能清晰呈现"证据 + 选项 + 影响"的界面**。在终端里读一段长文本然后选 1/2/3，无法承载这种决策质量 |
| **C · CI/CD 集成** | 开发团队 | 代码提交即触发、结果回写工单/PR | **需要 CLI + 无界面 API**。UI 完全无关 |
| **D · 学习与 CTF 快速试** | 学生 / 新手 | 低摩擦启动、快速看结果 | CLI 更快；但也需要看证据与推理过程 |

**场景 C 决定必须有 CLI；场景 A 与 B 决定必须有 WebUI。两者不是替代关系。**

### 2.2 竞品形态对照

| 项目 | 交付形态 | 实际体验结论 |
|---|---|---|
| **PentAGI** | 自托管 Web + REST/GraphQL + 安装器 TUI | 平台完整度在开源进攻性 Agent 中**属第一档**；Go 单体 + Compose 全家桶，比 Python 研究原型更接近可运维平台 |
| **PentestGPT** | CLI（+ legacy 交互模式） | 学习与 CTF 的标杆，但**无状态可视化**，长任务观察困难 |
| **Strix** | CLI（偏 AppSec + 修复闭环） | 开发者工具感强，适合 CI 场景 |
| **HexStrike AI** | **MCP server，无自有 UI** | **反面教材**：UI 完全外包给第三方客户端（5ire / Claude Desktop）。独立实测反馈：工具参数错误、超时、**大目标下客户端挂死** |
| **CAI** | CLI + TUI + iOS（PRO 商业版） | 核心仍是 CLI；移动端是商业增值方向，不是技术必需 |
| **Shannon** | CLI（白盒 Web/API） | 白盒场景够用，因为流程线性 |
| **Zen-AI-Pentest** | FastAPI + WebSocket 实时更新 | 有 Web 层，方向正确 |

**从对照中得出两条结论：**

1. **有 Web 层的项目（PentAGI）完整度明显更高**，且其可观测性栈（Langfuse + OTel + Grafana）本身就需要图形界面才可用。
2. **把 UI 外包给第三方客户端的项目（HexStrike）体验不可控** —— 因为 MCP 客户端不知道 Aletheia 的领域概念（证据链、光圈投影、冲突矩阵），无法为它们设计合适的界面。

### 2.3 本项目的特殊性：三个能力天生需要图形界面

这是最根本的理由。本项目相对竞品的差异化集中在三处，而它们在结构上**无法用命令行有效表达**：

| 能力 | 数据结构 | 为什么 CLI 表达不了 |
|---|---|---|
| **① 证据链** | `finding → assertions → evidence → exec_id → 原始输出行号` 的**多级树 + 交叉引用** | 一条证据可能支撑多个断言，一个断言可能依赖多条证据。CLI 只能线性输出，用户无法看出全局关系 |
| **② 光圈上下文投影** | 「本次上下文装了哪些实体 / 省略了哪些维度 / 为什么选它们（`selection_reasons`）/ 预估 token 占比」 | 这是**本项目最核心的创新**，但它是一个"视野与取舍"的可视化问题。文本形式下用户只能看到最终结果，看不到取舍过程 |
| **③ 冲突矩阵** | 三路观测（黑盒 / 白盒 / 二进制）结果的 **4 象限矩阵** | 二维矩阵天然适合图形；文本只能逐条罗列，**"打不通但有缺陷"这个最高价值象限会被淹没在列表里** |

**结论：如果只有 CLI，这三个能力用户感知不到，项目会退化成一个普通的 CLI 渗透 agent —— 而这个赛道上已经有 PentestGPT、Strix、hackingBuddyGPT 等成熟产品。**

**WebUI 不是"顺便提供"，它是差异化能力的呈现载体，是本项目的必需品。**

### 2.4 为什么不做桌面 GUI

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Electron 桌面端 | 原生窗口体验 | 包体 100MB+；Chromium 版本维护；三平台构建矩阵；**且功能与浏览器版完全重叠** | 收益不抵成本 |
| Tauri | 包体小（~10MB） | 引入 Rust 前端构建链，与已有技术栈叠加；仍需三平台构建 | v1.0 不做，若后续确有需求可低代价追加（前端代码可复用） |
| 本地服务 + 浏览器 | 零额外分发；跨平台天然一致；**且"服务 + 浏览器"架构本身就支持远程访问（团队模式）** | 需要用户手动打开浏览器 | **采纳** |

**关键论据：** 采用"服务 + 浏览器"架构后，桌面端与团队服务端**共用同一套前端代码**。而 Electron 方案会把这套代码锁死在单机场景。

### 2.5 为什么不做移动端

| 论据 | 说明 |
|---|---|
| **操作性质不匹配** | 渗透测试是长时间、高信息密度、需要精细操作的工作。触屏交互在"读证据链 / 看冲突矩阵"这类任务上是劣势 |
| **竞品证据** | CAI 的 iOS 端是 **PRO 商业版的增值功能**（€350/月），定位是"移动中监控任务"，而非核心工作流。它证明的是商业可能性，不是技术必要性 |
| **成本** | 移动端需要独立的前端技术栈（Swift/Kotlin 或 RN）与发布流程（App Store 审核），对开源项目是沉重负担 |
| **替代方案** | WebUI 采用响应式布局即可满足"手机上瞄一眼进度"的需求，成本几乎为零 |

**决议：v1.0 与 v2.0 均不做原生移动端。** WebUI 做基础响应式适配（保证手机上能看进度与批准决策），不做移动端专项优化。

## 3. 载体清单与职责边界

**核心原则：四个载体职责不重叠。任何一个功能只有一个"主承载"。**

### 3.1 `alethd` 守护进程（核心服务）

| 项 | 内容 |
|---|---|
| **语言** | Go（单二进制） |
| **职责** | 承载全部业务逻辑；对外暴露 API（Protobuf over gRPC + 浏览器的 HTTP/JSON 映射） |
| **必须做** | 会话生命周期管理、状态持久化、任务执行、全部模块调度 |
| **不做** | 不做任何 UI 渲染 |
| **关键约束** | 默认仅监听 `127.0.0.1`（对 D19 的回应：安全默认） |

### 3.2 `aleth` CLI（控制平面）

| 项 | 内容 |
|---|---|
| **语言** | Go（与 daemon 同代码库，共用 API 客户端） |
| **职责** | **控制平面**，不是渗透会话的主界面 |
| **必须做** | ① 启动/停止/重启 daemon ② 会话状态查询（`aleth status`）③ 脚本化批量操作 ④ CI 集成（无界面模式）⑤ 报告导出 ⑥ 范围与授权凭证录入 |
| **不做** | ❌ 不做交互式渗透会话的主界面（那是 WebUI）❌ 不做实时进展的可视化（`status` 只给摘要）❌ 不做证据链浏览（可导出，但浏览用 WebUI） |
| **设计取向** | 面向"脚本可组合"而非"人机对话" |

**典型用法：**

```bash
# 启动服务（后台守护）
aleth daemon start

# CI 场景：无界面运行 + 结果回写
aleth run --scope roe.yaml --target ./app --no-ui --report sarif --out report.sarif

# 状态查询（脚本可解析）
aleth status --session sess_018f... --format json

# 导出证据链供审计
aleth export --session sess_018f... --format evidence-bundle --out ./audit/
```

### 3.3 WebUI（主界面）

| 项 | 内容 |
|---|---|
| **技术** | React + TypeScript + Vite（**不做 SSR**） |
| **职责** | **渗透会话的主界面**，也是本项目差异化能力的唯一完整呈现载体 |
| **必须做** | ① 会话总览与创建 ② 实时执行流观察 ③ 心智地图浏览 ④ **证据链视图** ⑤ **光圈上下文视图** ⑥ **冲突矩阵视图** ⑦ 人机协同决策队列 ⑧ 报告与导出 ⑨ 范围与授权管理 ⑩ 成本与预算面板 |
| **不做** | ❌ 不做首次配置向导（用 CLI，避免引导用户在没有授权凭证时启动）❌ 不做模型 API Key 管理（配置文件 + 环境变量，避免前端接触密钥） |
| **关键约束** | 凭据不入前端，全部经 Privacy Gateway 脱敏（见 `02` §11.3） |

### 3.4 MCP 接口（集成）

| 项 | 内容 |
|---|---|
| **方向** | **双向** |
| **作为消费者** | 消费外部 MCP server 提供的工具（对齐 pentestagent 的双向 MCP 做法） |
| **作为提供者** | 把 Aletheia 的能力暴露为 MCP server，让 Claude Desktop / Cursor 等外部 agent 调用 |
| **必须做** | 工具调用代理（含参数化 Schema 校验、范围校验、脱敏） |
| **不做** | ❌ **不把 UI 外包给 MCP 客户端** —— 这正是 HexStrike 的教训。MCP 客户端不知道 Aletheia 的领域概念，无法为证据链、光圈投影、冲突矩阵设计合适界面 |
| **关键约束** | 通过 MCP 暴露的能力必须与 WebUI/CLI 遵循**完全相同的**闸门与范围校验，不得有绕过路径 |

## 4. 明确排除的载体与理由（汇总）

| 载体 | 决议 | 三条理由 |
|---|---|---|
| **桌面 GUI（Electron）** | ❌ | ① 包体与维护成本 ② 功能与浏览器版完全重叠 ③ 会锁死单机场景，无法复用前端代码到团队模式 |
| **桌面 GUI（Tauri）** | ⏸ 暂缓 | 前端代码可复用，若后续确有需求可低代价追加（不作为 v1.0 范围） |
| **移动 App** | ❌ | ① 操作性质不匹配（触屏不适合高信息密度任务）② 竞品证明其属增值功能而非核心 ③ 独立技术栈 + 审核流程成本过高。**替代：WebUI 响应式适配** |
| **浏览器扩展** | ❌ | 与主界面重叠，且浏览器扩展是常见攻击面 |
| **第三方客户端托管 UI** | ❌ | HexStrike 教训：实测客户端挂死、参数错误、无状态可视化 |

## 5. 部署形态

**同一套代码库，两种部署模式，通过配置切换。**

### 5.1 单机模式（默认，面向个人研究者 / 学生 / CTF）

| 项 | 内容 |
|---|---|
| 启动方式 | 一条命令，浏览器自动打开 `http://127.0.0.1:<port>` |
| 存储 | SQLite（WAL）+ 文件系统内容寻址 |
| 依赖 | 无外部数据库；仅工具沙箱需要 Docker |
| 认证 | 无需登录；启动时生成一次性访问令牌（防本机其他进程访问） |
| 监听 | **仅 127.0.0.1**（安全默认，D19） |
| 可观测性 | WebUI 内置轻量查看器（无需 Grafana） |
| 适用迭代 | I0 起即可用 |

### 5.2 团队模式（面向企业红队）

| 项 | 内容 |
|---|---|
| 部署 | 服务端常驻；WebUI 通过反向代理访问 |
| 存储 | PostgreSQL + Apache AGE；原始输出走共享卷或对象存储 |
| 多用户 | 用户 + 角色权限（操作员 / 观察者 / 审计员） |
| 分布式 | 远程 worker 节点（控制面与执行面分离，对齐 PentAGI 的生产建议） |
| 认证 | OIDC 或内置账号体系；强制 TLS（无证书时**拒绝**对外暴露而非自签降级） |
| 可观测性 | OTel + Grafana/Loki（可选自托管） |
| 适用迭代 | P3 之后（v1.0 不做，但架构预留） |

**关键设计：** 两种模式共用同一套数据模型（schema 差异由驱动层吸收）与同一套前端。**团队模式不是另做一个产品，而是同一产品的配置升级。**

## 6. WebUI 信息架构

### 6.1 页面清单

| # | 页面 | 优先级 | 核心内容 |
|---|---|---|---|
| 1 | **会话总览** | P0 | 会话列表、状态、成本、进度、风险摘要 |
| 2 | **实时执行流** | P0 | agent 动作时间线、当前任务、工具调用、实时输出流 |
| 3 | **心智地图浏览器** | P1 | 7 类实体的图视图 + 表视图双模；按类型/来源/置信度筛选 |
| 4 | **★ 证据链视图** | **P1** | 从 finding 出发的树形展开；双向引用；一键定位原始输出行号；复现脚本展示 |
| 5 | **★ 光圈上下文视图** | **P1** | 每次装配的实体清单、被省略维度、`selection_reasons` 可视化、token 占用分布 |
| 6 | **★ 冲突矩阵视图** | **P2** | 三路观测的 4 象限矩阵；点击象限下钻到具体冲突 |
| 7 | **人机协同决策队列** | P1 | 待决策项卡片（证据 + 选项 + 影响评估）；批准/拒绝/改写 |
| 8 | **报告与导出** | P2 | 分层报告浏览（主报告 / 附录 / 调试）；导出 Markdown / PDF / SARIF |
| 9 | **范围与授权管理** | P0 | 授权凭证、scope 定义、越界拦截记录（审计） |
| 10 | **成本与预算面板** | P1 | 实时消耗、按任务/agent 分布、光圈档位与预算关系、熔断阈值线 |

### 6.2 三个核心视图的设计意图

**★ 证据链视图** —— 把"可证明性"变成看得见的东西。

```
finding_xxx  越权访问 /api/v2/orders/{id}
 ├─ 状态: ✅ CONFIRMED（已独立复现）
 ├─ 断言
 │   ├─ EXISTENCE   端点接受任意 order_id          ──▶ ev_001
 │   └─ DATA_ACCESS 返回他人订单完整数据            ──▶ ev_003
 ├─ 证据
 │   ├─ ev_001  httpx  GET /api/v2/orders/1001 → 200   exec_a1b2
 │   ├─ ev_002  httpx  GET /api/v2/orders/9999 → 403   exec_c3d4
 │   └─ ev_003  session_B 请求 order_1001 返回 username=alice   exec_e5f6
 │            └─ 副作用观测: DATA_RETURNED (matched: "username":\s*"[^"]+")
 ├─ 复现
 │   └─ 3 步 · 环境哈希 7f3a... · 上次复现 2026-09-24 15:22 成功
 └─ 归因校验: ✅ 双向一致（无 ATTRIBUTION_MISMATCH）
```

**这张图就是"不会说谎"的证明。** 没有这一视图，用户无法验证系统是否在幻觉；有了它，每个结论都可以当场核对。

**★ 光圈上下文视图** —— 把"取舍"变成看得见的东西。

```
本次装配  f/4  ·  预算 8,000 token  ·  实际 7,412 (92.6%)
 ├─ 入选实体 (54)
 │   ├─ score 1.00  svc_018f..  443/tcp nginx 1.24.0
 │   ├─ score 0.87  ept_018a..  /api/v2/orders/{id}
 │   └─ ...
 ├─ ⚠ 因预算省略
 │   ├─ TIMELINE 全量（保留最近 3 条）
 │   └─ ASSET 属性深度降为 1
 └─ ℹ 未入选的高分实体 (12)
     └─ score 0.61  svc_018e..  8080/tcp tomcat  ← 建议提高光圈档位
```

**这一视图让用户能判断"系统是不是漏看了什么"。** 它同时是 M3 召回率问题的诊断工具。

**★ 冲突矩阵视图** —— 把最高价值的信号放到最显眼的位置。

```
              白盒: 有缺陷        白盒: 无缺陷
黑盒: 可利用    ✅ 双源确认 (7)      ⚠ 白盒漏检? (2)
黑盒: 打不通    ★ 深度优先 (11)     ○ 低优先级 (34)
                 ↑ 最高价值象限
```

**11 个"打不通但有缺陷"的目标是本次评估最有价值的部分** —— 它们是链式漏洞的候选第一环。在纯 CLI 输出里，这 11 条会混在 54 条结果中。

## 7. 关键交互设计

### 7.1 人机协同决策卡片

调研结论：全自主 21% vs 有人类提示 64%，且 AIxCC 亚军 Buttercup 采用"置信度 <98% 需人工复核"。人类介入点是**设计而非缺陷**。

决策卡片必须包含四个要素：

| 要素 | 内容 | 为什么必须 |
|---|---|---|
| **证据摘要** | 支撑该决策的关键证据（可展开到完整证据链） | 让人类能独立判断，而非盲信 agent 的总结 |
| **选项** | 具体可选项（如：继续深挖 / 换攻击路径 / 跳过 / 终止） | 避免"只能批准或拒绝"的伪选择 |
| **影响评估** | 每个选项的预期成本、时间、风险 | 让决策有依据 |
| **不确定性标注** | agent 自己的置信度 + 已知的信息缺口 | 防止人类被"看起来很确定"的表述误导 |

**触发复核的条件：** 置信度低于阈值（可配置，默认 0.98）/ 涉及会话终止 / 涉及范围边界 / 成本超预算 50% / 出现归因冲突。

### 7.2 长任务与断线重连

| 设计 | 说明 |
|---|---|
| 状态在服务端 | 浏览器完全无状态；关闭浏览器不影响任务 |
| 重连恢复 | 重新打开即回到当前状态（含实时流的历史补全） |
| 实时通道 | WebSocket（或 SSE），断线自动重连并补发增量 |
| 时间回放 | **可拖动时间轴查看任意历史时刻的认知状态**（依赖 M2 的 `SnapshotAt` 与 M6 的 Checkpoint） |

**时间回放是本项目独有的能力** —— 它把"攻击路径可回溯"从日志功能变成了可交互的界面功能。

### 7.3 轻量优先原则

| 原则 | 说明 |
|---|---|
| 不做重型前端框架生态 | 状态管理用轻量方案，避免引入大型全家桶 |
| 不做 SSR | 本地工具无 SEO 需求；SSR 会增加部署复杂度 |
| 首屏即用 | 单机模式下打开即可用，无登录、无引导 |
| 响应式但不做移动专项 | 手机上能看进度、能批准决策即可 |

## 8. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | **React + TypeScript** | 生态成熟；与 PentAGI 同路线；团队熟悉度高 |
| 构建 | **Vite** | 快；本地工具无需复杂构建优化 |
| 图可视化（心智地图 / 证据链） | 轻量图库（按需选型，倾向可自定义渲染的方案） | 证据链是树 + 交叉引用，通用图库需支持自定义节点 |
| 实时通信 | WebSocket（降级 SSE） | 双向交互需求（决策提交） |
| API 契约 | 从 `05` 的 Protobuf 生成 TypeScript 类型 | **前端类型与后端契约同源**，避免手工同步漂移 |
| 状态管理 | 轻量方案（按需引入，避免大而全） | 本地工具场景不复杂 |
| 打包 | 静态资源嵌入 Go 二进制（`embed`） | **单二进制分发** —— 用户只需 `alethd` 一个文件 |

**最后一条是关键交付优势：** 前端构建产物嵌入 Go 二进制后，用户下载一个文件即可运行完整系统（含 UI），无需 Node 环境。这直接消解了"桌面 GUI 才能有好的分发体验"这一论点。

## 9. 与架构的映射

哪些架构能力需要哪个载体承载：

| 架构能力 | 承载载体 | 说明 |
|---|---|---|
| 工具执行（M1） | 无界面 | 后台运行 |
| 心智地图（M2） | **WebUI 页面 3** | 图形是唯一能表达图结构的方式 |
| 光圈控制（M3） | **WebUI 页面 5** ★ | 取舍过程必须可见 |
| 证据账本（M4） | **WebUI 页面 4、8** ★ | 证据链是"不能说谎"的证明界面 |
| 编排（M5） | **WebUI 页面 2** + CLI | 实时流靠 WebUI；脚本化靠 CLI |
| 范围内核（M6） | **WebUI 页面 9** + CLI | 授权凭证录入用 CLI（避免无凭证时启动 UI） |
| 隐私网关（M6） | 无界面 | 透明运行；仅在拦截时产生告警 |
| 成本治理（M6） | **WebUI 页面 10** | 预算与光圈关系的可视化 |
| 三路融合（M7） | **WebUI 页面 6** ★ | 冲突矩阵是二维结构 |
| 业务逻辑（M8） | WebUI 页面 4 + 7 | 契约与违背对比需要并排呈现 |
| 评测（M9） | CLI（主）+ WebUI（结果浏览） | 评测是批处理任务 |

**★ 标记的三处，正是选择 WebUI 为主界面的直接原因。**

## 11. 范围蔓延防护

以下需求**当前明确拒绝**，理由记录在此以免重复讨论：

| 需求 | 决议 | 理由 |
|---|---|---|
| 做成 SaaS 在线服务 | ❌ 拒绝 | 与"数据主权"第一原则直接冲突；且渗透测试数据高度敏感 |
| 提供浏览器插件 | ❌ 拒绝 | 与主界面重叠；扩展是常见攻击面 |
| 做移动 App | ❌ 拒绝（v1.0/v2.0） | 见 §4 |
| 做 Electron 桌面端 | ❌ 拒绝 | 见 §2.4 |
| 支持多租户 SaaS 计费 | ❌ 拒绝 | 这是商业产品需求，开源项目不承担 |
| 提供 REST API 给第三方开发者做 UI | ⏸ 暂缓 | API 是有的（daemon 本就暴露），但**不承诺 API 稳定性**，也不为第三方 UI 做适配 |
| 接入 Slack / 钉钉等 IM 通知 | ⏸ 暂缓至 P3 | 成本低但非核心；需要时通过 webhook 即可，不需要内建 IM 集成 |

## 12. 决策速查

| 问题 | 答案 |
|---|---|
| 主要用什么？ | **浏览器打开 WebUI** |
| 服务器上没浏览器怎么办？ | 用 `aleth` CLI（控制平面）+ 无界面模式 |
| 能不能只装 CLI 不装 WebUI？ | 前端资源嵌入同一二进制，体积影响很小；如需极小镜像可编译 `--no-web` 变体 |
| 能不能远程用？ | 单机模式默认仅 127.0.0.1；团队模式支持远程（需 TLS） |
| 手机上能用吗？ | 能看进度、能批准决策（响应式适配）；不做移动专项优化 |
| 有桌面客户端吗？ | 没有，也不计划做 |
| 能在其他 agent 里调用吗？ | 可以，通过 MCP 接口（P2 交付） |
| 为什么不做桌面端？ | 服务 + 浏览器共用同一套前端，且天然支持团队模式；桌面端会锁死单机场景 |
