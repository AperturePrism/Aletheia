## 0. 这份文档是什么

你将接手 Aletheia 的完整开发工作。这份文档不重复架构设计（那些在 `02` 与 `modules/` 里），它只解决四个问题：

| # | 问题 |
|---|---|
| 1 | **开工前你必须知道什么**（避免用错误的假设开始） |
| 2 | **什么事你绝对不能做**（红线，做了就要回滚） |
| 3 | **什么事你不能自己决定**（必须请示） |
| 4 | **哪些"看起来像改进"的操作实际上是跑偏**（本项目最容易犯的错） |

**请把 §4（十条红线）与 §6（禁止的好心优化）当作硬约束读两遍。** 这个项目有大量"看起来保守、实际必要"的设计决策，它们不是随意选的，每一条背后都有调研证据。

## 1. 项目速览

| 项 | 内容 |
|---|---|
| **团队** | AperturePrism（光圈 + 棱镜） |
| **项目** | Aletheia（古希腊语"去蔽"）—— 以"可证明性"为第一原则的自主渗透测试系统 |

| **起点** | 迭代 **I0 · 仓库骨架与抽象层** |

**三个"第一"（这是项目存在的理由，别忘了）：**
1. 第一个把"证据"作为一等数据结构（而非事后补 PoC）的 AI 渗透系统

3. 第一个给出可复现的业务逻辑漏洞检出数字的系统

**如果开发过程中这三个"第一"被削弱了，无论功能完成了多少，都是跑偏。**

## 4. 不可协商的十条红线 ★

**违反任意一条，产出必须回滚。没有例外，没有"这次特殊情况"。**

### R1 · 不得修改 `05-接口契约与数据模型.md`

**规则：** 该文档已冻结。任何变更必须走独立 PR，标题前缀 `contract:`，且需双人 review（其中一人必须是 M4 反幻觉负责人）。

**为什么：** 契约是 Go/Python 之间、模块之间的唯一约定。允许实现者顺手改契约，等于取消了"契约定死、实现可变"这个架构基础。**你可以在实现中发现契约不合理，但正确做法是提出 `contract:` PR，而不是边实现边改。**

### R2 · 不得放宽 Q3 / Q4 / Q5 三条红线门禁

| 门禁 | 内容 |
|---|---|
| **Q3** | 伪造证据注入 100% 被拒 |
| **Q4** | 越界 100% fail-closed |
| **Q5** | 抓包零真实值泄漏 |

**为什么：** 这三条分别对应"不会说谎""不会越界""不会泄密"。它们不是质量指标，是**存在前提**。放宽它们，项目就失去立项理由。

### R3 · 不得为了让测试通过而削弱测试本身

**禁止的所有形式：**

| 禁止行为 | 具体表现 |
|---|---|
| 放宽断言 | 把 `assert result.status == CONFIRMED` 改成 `assert result.status is not None` |
| 注释掉用例 | `# test_injection_rejected  # TODO: fix later` |
| 改成跳过 | `@pytest.mark.skip(reason="flaky")` |
| 抽样代替全量 | 把"100% 被拒"改成"抽查 10 个通过" |
| mock 被验证对象 | 把 Assertion Verifier mock 掉，然后"验证"它工作 |
| 改断言目标 | 断言一个自己实现的简化版函数，而非真实路径 |

**为什么：** 反幻觉与范围控制是本项目的核心资产，它们的测试**就是产品本身**。削弱测试等于削弱产品，但会伪装成"进度正常"。

**如果测试无法通过：** 停在原地，按 §5 请示。**绝不通过修改测试让它变绿。**

### R4 · 不得引入绕过 Evidence Ledger 的 finding 路径

**规则：** 任何产出"发现"的代码路径，必须经由 `LedgerService.ValidateAssertion` 走四道闸门。**不存在任何其他方式让一个结论变成 CONFIRMED。**

**检查方法：** 搜索是否存在直接构造 `Finding{item.status = CONFIRMED}` 的代码。这类代码是 P0 缺陷。

**为什么：** 对齐原则 P-3。一旦存在旁路，本项目的第一个"第一"就不成立了。

### R5 · 不得让 LLM 参与命令行生成

**规则：** 工具调用的 argv 必须由参数化 Schema **确定性渲染**。**任何形如 `run(f"nmap {llm_output}")` 的代码都是违规的。**

**为什么：** 这是对调研中真实翻车案例的直接回应 —— HexStrike 类项目因 LLM 拼参数导致"扫描了完全超出范围的目标"。参数化 Schema 也可同时消除注入、参数名不匹配、ANSI 污染三个问题。

### R6 · 不得让 agent 拥有终止会话的权限

**规则：** `TerminationService.RequestTermination` 是系统**唯一**的会话终止入口（除熔断外）。任何 `return` / `sys.exit` / `session.close()` 形式的自行终止都是 P0 缺陷。

**为什么：** 消除调研缺陷 D3（Flag 幻觉）—— 实测中 agent 发现一段随机哈希就宣告成功并**立即终止会话**，换更强的模型也无法解决。只有"无权终止 + 独立仲裁"能治。

### R7 · 不得绕过 Privacy Gateway

**规则：** 真实敏感值（IP / 域名 / 凭据 / 内部路径）**不得**出现在送往模型的任何内容中。Gateway 默认强制开启，**不得提供 UI 开关**，只能通过配置文件显式禁用（且禁用时启动日志必须高亮告警）。

**为什么：** 数据主权是行业空白 G6，也是本项目对企业场景的核心价值。

### R8 · 不得修改 Scope Kernel 的判定逻辑

**规则：** 三重校验（network / tool_param / post_dns）与"默认拒绝"语义不得修改。**越界必须熔断整场会话，不得改成"跳过该请求继续"。**

**为什么：** 这是 `07-threat-model.md` 中 R4 的结论 —— **提示词层面的防御最终会被绕过，所以真正的防线是 Scope Kernel 这个物理约束**。动它等于拆掉最后一层。

### R9 · 不得省略三个核心视图

| 视图 | 为什么不可省 |
|---|---|
| **证据链视图** | 用户验证"系统是否在幻觉"的唯一界面 |
| **光圈上下文视图** | 诊断"系统是不是漏看了什么"的唯一界面 |
| **冲突矩阵视图** | "打不通但有缺陷"这个最高价值象限的唯一呈现方式 |

**允许简化视觉细节（配色、动画、布局精修），不允许省略功能与信息密度。**

**为什么：** `06` §2.3 论证过 —— 如果这三个能力用户感知不到，项目会退化成普通 CLI 渗透 agent，而那个赛道已有 PentestGPT、Strix 等成熟产品。

### R10 · 不得在未达门禁时进入下一阶段

**规则：** `04` 中每个阶段的门禁是**硬门禁**。P0 未通过，不得开始 P1 的工作。

| 阶段 | 门禁 |
|---|---|
| P0 | 24h 无崩溃 · 伪造证据 100% 被拒 · 越界 100% fail-closed · 隐私抓包零泄漏 · 预算耗尽必熔断 |
| P1 | 实体召回率 ≥95% · 超预算装配必然拒绝 |
| P2 | 公开基准可复现分数 · 业务逻辑首个可复现数字 |
| P3 | 143h 无崩溃 · 成本降 ≥60% |

**为什么：** 对齐 AIxCC 的核心教训 —— **"技术先进与工程可靠是两回事"**。多数参赛队伍因系统崩溃、配置错误丢分，而不是因为技术不够先进。**先立地基，再堆能力。**

## 6. 禁止的"好心优化" ★★

**这一节是本项目最容易被跑偏的地方。** 以下行为都出于善意，但都会破坏项目根基。

| # | 看似合理的做法 | 为什么是跑偏 | 正确做法 |
|---|---|---|---|
| **1** | "这个校验太严了，先注释掉，跑通再说" | 校验是产品本身，不是障碍。注释掉等于删除功能 | 停下来问为什么不过 |
| **2** | "加个 try/except 让它别崩" | **会把 fail-closed 变成 fail-open**。原则 P-4 明确要求"失败即熔断，不降级" | 异常必须向上传播并触发熔断 |
| **3** | "门禁测试太慢，改成抽样/降频" | Q3/Q4/Q5 是红线，**不可抽样** | 优化测试执行速度，但不减覆盖 |
| **4** | "这部分先用 mock 数据，以后再接真实实现" | mock 会掩盖契约不一致，也让测试失去意义 | 若必须 mock，只能 mock **外部边界**（如模型 API、网络），不得 mock 被验证对象 |
| **5** | "UI 先做简化版，以后再美化" | 简化视觉可以；**简化功能与信息密度不可以**（R9） | 明确区分"视觉简化"与"功能简化" |
| **6** | "先跑通功能，安全机制后面再加" | 安全是地基不是装饰。I2/I3 排在能力层之前就是这个原因 | 按迭代顺序做，不跳步 |
| **7** | "这个测试失败可能是环境问题，先跳过" | 环境问题也是问题。P0 门禁包含 24h 稳定性测试，正是为了暴露这类问题 | 定位根因，不要跳过 |
| **8** | "文档写错了，我按代码改文档" | **文档是设计意图，代码是可能出错的实现。顺序不能反** | 见 §9 |
| **9** | "顺手重构一下这段代码，让它更优雅" | 无关重构会污染 commit，让后续自检无法聚焦 | 重构单独提 PR，与功能 commit 分开 |
| **10** | "这个依赖更好/更快，我换掉" | 技术选型已定（`02` §7）。换依赖需请示 | 按 §5 请示 |
| **11** | "用 LLM 来做这个解析，更灵活" | 违反 P-2（确定性优先）。解析器必须是确定性的、可测试的、字节级可复现的 | 写确定性解析器 + 边界用例测试 |
| **12** | "让 agent 自己判断下一步，更智能" | 违反 CHECKMATE 教训。长程规划交给确定性规划器，LLM 只生成任务图 | 按 `modules/M5` §2 实现 |
| **13** | "用字符串匹配判断利用是否成功，简单" | **这正是 D1 幻觉式成功的根因**。实测中出现"23/23 攻破实际 0 个 shell" | 用强制证据模式 + 副作用观测（`modules/M4` §4.2 G-3） |
| **14** | "把上下文塞满，让模型信息更全" | 违反光圈设计。上下文有硬预算，超预算必须拒绝而非截断 | 按 `modules/M3` 装配 |
| **15** | "冲突的数据合并一下，保持整洁" | 冲突是**最高价值信号**，不是噪声。合并会消灭它 | 用 `CONTRADICTS` 关系保留多版本（`modules/M7`） |

**记住一句判断标准：如果某个改动让系统"更容易跑通但更不容易验证"，那一定是跑偏。**

## 7. 本项目特有的陷阱

这些是从调研的 20 项缺陷（D1–D20）里提炼的，你的代码里最容易复现它们：

| 陷阱 | 表现 | 对策落点 |
|---|---|---|
| **把上下文当记忆** | 早期发现被挤出上下文后永久丢失 | 记忆在 M2 图里，上下文只是投影 |
| **吞掉异常** | `except: pass` 让失败静默 | fail-closed，异常必须触发熔断 |
| **工具参数自由拼接** | 用字符串格式化构造命令 | 参数化 Schema → 确定性 argv |
| **解析用正则硬凑** | 没有边界守卫，遇到变体就错 | 类型断言 + 边界用例（含 ANSI、前导数字、CRLF） |
| **判定成功用关键字** | `if "success" in output` | 副作用观测 + 模式库 |
| **报告里混入推测** | 把 Hypothesis 当结论写进去 | 类型系统层面已排除（`05` §7.2） |
| **让 LLM 决定终止** | agent 自认为完成就退出 | 必须经 Arbiter |
| **把量当价值** | 追求 finding 数量 | 分层报告，主报告仅 CONFIRMED |
| **默认配置不安全** | 自签证书、默认口令、监听 0.0.0.0 | 安全默认（D19） |
| **遥测默认开启** | 悄悄上报数据 | 零遥测默认（D18） |

## 8. 提交规范

### 8.1 Commit 前缀

| 前缀 | 用途 |
|---|---|
| `feat(M3):` | 新功能（模块号必填） |
| `fix(M4):` | 缺陷修复 |

| `refactor:` | 重构（不得与功能混在同一 commit） |
| `chore:` | 构建/依赖/杂项 |

### 8.2 PR 自检清单

```markdown
- [ ] 本次改动对应的迭代是：I__
- [ ] 涉及模块：M__
- [ ] 是否修改了 `05` 契约？是/否（若"是"，标题须含 `contract:`）
- [ ] 是否新增 LLM 调用？是/否（若"是"，已在描述中说明为何无法确定性实现）
- [ ] 是否新增第三方依赖？是/否
- [ ] 是否触碰 Q3/Q4/Q5 相关代码？是/否（若"是"，附测试证据）
- [ ] 是否修改了测试？若修改，说明是"补充"还是"调整"（调整必须说明理由）
- [ ] 本地已通过：`make build && make test && make lint`
- [ ] 增量检查：Q1–Q14 哪些已覆盖？哪些未覆盖？未覆盖原因？
- [ ] 若本迭代含「前端交付物」，是否一并提交？
```

### 8.3 禁止的提交行为

- ❌ 在 `main` 上直接提交
- ❌ 跳过 CI（`--no-verify`）
- ❌ 功能与重构混在同一 commit
- ❌ 提交中含真实目标信息（用靶场数据或文档示例）
- ❌ 提交中含真实凭据（用假的占位符）

## 9. 文档冲突时的优先级

**当文档之间、或文档与你的理解冲突时，按此顺序裁决：**

| 优先级 | 依据 | 说明 |
|---|---|---|
| **1（最高）** | `05-接口契约与数据模型.md` | 契约是冻结的。实现与契约冲突 → **改实现** |
| **2** | `07-threat-model.md` + `08-授权与交战规则规范.md` | 安全与授权不可妥协 |
| **3** | `modules/Mx`（当前模块） | 模块级设计细节 |
| **4** | `02-架构设计文档.md` §2（设计原则） | 五条原则与 D1–D20 对策 |
| **5** | `04-开发总纲` | 流程、DoD、门禁 |
| **6** | `06-交付形态` | 载体与界面 |
| **7（最低）** | 你的判断 | 仅在前六项都不覆盖时适用 |

**关键规则：文档与代码冲突时，以文档为准。** 代码是可能出错的实现，文档记录的是设计意图。**如果要改文档，那是另一件事 —— 先请示（§5）。**

**发现文档确实有错时：** 明确指出错误、给出证据、提出修正建议。**不要默默按自己的理解实现。**

## 10. 完成一个迭代要交什么

| # | 交付物 | 说明 |
|---|---|---|
| 1 | 代码 | 满足该迭代全部交付物（含「前端交付物」） |
| 2 | 测试 | 覆盖该迭代的全部测试要求，Q1–Q14 中适用项全绿 |
| 3 | **DoD 达成报告** | 逐条对照 `04` 中该迭代的 DoD，**逐项标注：达成 / 部分达成 / 未达成** |
| 4 | **偏差说明** | 任何未达成项必须说明：根因、影响、建议处置 |
| 5 | **契约变更清单** | 若本迭代有 `contract:` PR，列出变更点 |
| 6 | **新增 LLM 调用清单** | 每个新增调用说明为何无法确定性实现 |
| 7 | 文档回填 | 更新 `04` 中该迭代的实际达成情况（`04` 是活文档） |
| 8 | `CHANGELOG.md` 条目 | 记录变更与迁移指引 |
| 9 | **自检报告** | 按 `10` §5 模板产出，含十条红线专项核查（**每条附实际执行的命令与原始输出**） |

**第 3、4、9 项是硬要求。** **"未达成但已说明"是可以接受的；"未达成但未说明"是不能接受的。** 自检报告首先要保证的就是这三项的一致性。

## 11. 遇到不确定时的行为准则

按优先级排序：

| 顺序 | 动作 |
|---|---|
| 1 | **先查文档。** 大概率已经写过了（16 份文档覆盖了绝大多数决策） |
| 2 | **查唯一真源。** 按 `README.md` §3 的映射表定位到权威位置 |
| 3 | **查调研依据。** 设计决策的理由在 `01` 与 `02` §2 里 |
| 4 | **仍不确定 → 请示。** 不要基于假设写代码 |
| 5 | **永远不要**因为"看起来合理"就绕过红线 |

**一条心法：** 这个项目的每一个"看起来奇怪"的设计，背后都有一条调研证据。**在你决定改动它之前，先找到那条证据** —— 如果你找不到，说明你可能漏读了什么。
