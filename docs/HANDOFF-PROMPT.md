## 四、不可协商的约束（违反即回滚，没有例外）

这五条是从 `09` §4 抽出来的、最容易在无意识中违反的。完整十条见 `09`。

1. **不得修改 `docs/05-接口契约与数据模型.md`。** 契约已冻结。发现它不合理 → 提
   `contract:` PR + 双人 review，不要边实现边改。`proto/aleth/v1/aletheia.proto`
   是它的机器可读形式，同样受此约束。
2. **不得放宽 Q3/Q4/Q5。** 伪造证据 100% 被拒 / 越界 100% fail-closed / 抓包零真实值
   —— 它们是项目的存在前提，不是质量指标。
3. **不得为了让测试通过而削弱测试。** 不放宽断言、不注释用例、不改成 skip、
  不用抽样代替全量、不 mock 被验证对象。测试过不去 → 停下来问。
4. **不得让 LLM 参与命令行生成。** argv 必须由参数化 Schema 确定性渲染。
   `run(f"nmap {llm_output}")` 这种代码是违规的。
5. **不得吞异常。** `except: pass` 会把 fail-closed 变成 fail-open。
   异常必须向上传播并触发熔断。

**一条判断标准**：如果某个改动让系统「更容易跑通但更不容易验证」，那一定是跑偏。

## 五、协作约定（与工具无关）

1. **每个迭代结束必须产出交接文档**，模板见 `docs/iterations/README.md`，
   实例见 `docs/iterations/I0-交接.md`。它假定接手方可能用完全不同的工具，
   所以每一步都要给**可直接执行的命令**，不写「用某工具打开某文件」。
2. **同时产出自检报告**（`docs/iterations/I{n}-自检报告.md`），十条红线逐条附
   实际执行的命令与原始输出。不接受「已检查」这类无证据结论。
3. **能用命令验证的，绝不靠判断。** 每个检查项对应一条命令；无法命令验证的
   必须显式标注「仅人工判断」并说明依据。
4. **未达成但已说明** 是可以接受的；**未达成但未说明** 不能接受。
5. Commit 前缀：`feat(M{n}):` / `fix(M{n}):` / `test(M{n}):` / `docs:` /
   `contract:` / `refactor:` / `chore:`。禁止在 `main` 直接提交，禁止跳过 CI。

## 维护提示

分隔线内的**第 2 节（当前状态）**与**当前 HEAD / tag** 是易腐信息。每次迭代结束后回填：

- HEAD 换成该迭代最后一个 commit
- tag 换成最新发布版本
- 「下一步」换成下一迭代的名称与开工要点

不更新的接手 Prompt 比没有更糟 —— 它会让人照着过期的计划开工，
而且看起来非常可信。这一点与 `docs/10` §0 的「绿灯替代有效」是同一类风险。

按 `docs/README.md` §5 的规则，本节是维护说明，不属于提示词正文；
提示词正文以两个分隔线之间的内容为准。
