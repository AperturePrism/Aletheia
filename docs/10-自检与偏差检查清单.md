> 版本：v2 ｜ 日期：2026-09-24
> 团队：**AperturePrism** ｜ 项目：**Aletheia**
> 用途：开发由 Claude Code **完整执行（含自检）**。本文件是自检标准 —— 把"是否跑偏"从主观判断变成**机器可验证的检查**。

## 0. 自检的固有困难（必读）

**自检最大的风险是"自己给自己打高分"。** 这不是态度问题，是结构问题 —— 记忆中的"我做了"与代码里的"实际有"之间存在系统性偏差。

三种典型失真：

| 失真 | 表现 |
|---|---|
| **记忆替代验证** | "我记得写了四道闸门" → 但没确认它们都在**主路径**上 |
| **绿灯替代有效** | "测试跑绿了" → 但没读测试代码，断言可能是空转的 |
| **相似替代一致** | "代码看起来符合契约" → 但字段名/类型/语义可能有偏差 |

**因此本文件的核心原则：能用命令验证的，绝不靠判断。**

三条硬要求：

| # | 要求 |
|---|---|
| **1** | 每个检查项必须对应**一条可执行命令或可观测结果** |
| **2** | 检查结论必须附**原始输出**（粘贴命令输出，不是复述"通过了"） |
| **3** | 无法用命令验证的项，必须显式标注"**仅人工判断**"并说明依据；这类项越少越好 |

**如果某个检查项只能人工判断，说明 CI 有缺口 —— 应把它补成自动化门禁（见 §8）。**

## 1. 自检的定位与边界

| 项 | 说明 |
|---|---|
| **自检对象** | 自己产出的**实际代码、测试、配置与文档**，而非记忆或意图 |
| **自检依据** | `05` 契约、`04` 的 DoD 与门禁、`09` 的十条红线、`02` §2 的设计原则 |
| **自检不是** | 代码风格审查、性能优化、功能设计讨论 |
| **自检的产出** | 一个明确结论：**可继续 / 需修正 / 必须回滚** |

### 1.1 铁律：只信证据，不信记忆

**"我打算做什么"和"我做了什么"是两件事；"我记得做了什么"和"代码里有什么"也是两件事。**

| 记忆/印象 | 必须做的验证 |
|---|---|
| "已实现四道闸门" | 打开闸门代码，确认四个检查点都在**主路径**上（不是只在测试里） |
| "测试全部通过" | 运行测试；**并读测试代码本身**，确认断言有效 |
| "已实现越界熔断" | 构造越界请求，观察是否真的熔断整场会话 |
| "契约未变更" | `git diff` 契约文件 |
| "UI 已完成" | 打开页面，检查信息密度，不只看"有没有页面" |

**任何"已完成"的声明，必须附可复现的证据（命令 + 原始输出）。无法给出证据的，视为未完成。**

## 2. 自检前必须准备好的证据材料

**这些材料同时也是迭代交付物的一部分。缺任何一项，自检结论都要标注"未验证"。**

| # | 材料 | 用途 | 缺失后果 |
|---|---|---|---|
| **1** | 本次改动范围清单（涉及哪些模块、哪些文件） | 限定自检范围 | 自检范围失控 |
| **2** | 当前迭代编号（如 I2） | 对照 DoD | 无法判定进度 |
| **3** | **完整测试运行日志**（非摘要） | 验证 Q1–Q14 | **无法验证门禁** |
| **4** | `git log` / PR 列表 | 检查 commit 规范与 `contract:` 前缀 | 无法验证 R1 |
| **5** | DoD 达成报告（逐条 + 证据） | 对照 P9 | 无法判定是否虚报 |
| **6** | 契约变更清单（若有） | 验证 R1 流程 | 无法验证契约漂移 |
| **7** | 前端页面截图（若有前端交付物） | 判定 R9 | 无法验证核心视图完整性 |

**强烈建议同时准备：** 测试覆盖率报告（区分"测试存在"与"测试有效"）、关键路径代码片段。

### P1 · 契约漂移

**定义：** 实现与 `05-接口契约与数据模型.md` 不一致；或修改了契约但未走 `contract:` PR 流程。

**典型表现：**

| 表现 | 示例 |
|---|---|
| 字段名/类型不符 | 契约是 `estimated_tokens: uint32`，实现用 `float` |
| 新增未定义字段 | 自行给 `EvidenceEntry` 加了 `confidence` 字段 |
| 语义不符 | 契约规定超预算返回 `APERTURE_OVER_BUDGET`，实现改为截断返回 |
| 静默改契约 | 直接编辑 `05` 文件，PR 标题无 `contract:` |
| 绕过接口 | 不走 `PrismService.Ingest`，直接写数据库 |

**检测方法：**

```bash
# 1. 契约文件是否被改动
git log --oneline -- docs/05-接口契约与数据模型.md
# 检查这些 commit 是否带 contract: 前缀

# 2. 接口实现与契约对比（人工）
# 打开 05 的目标章节，逐字段核对实现

# 3. 检查是否存在绕过接口的直连
grep -rn "INSERT INTO entity" --include="*.go" --include="*.py" core/ agents/
# 若出现，确认是否通过 PrismService

# 4. 检查状态机是否有未定义跃迁
grep -rn "CONFIRMED" --include="*.py" agents/
# 确认每个 CONFIRMED 赋值都经过 ValidateAssertion
```

**严重度：** 🔴 **P0**（契约是架构基础，漂移会导致 Go/Python 两侧不一致）

---

### P2 · 红线放宽

**定义：** Q3/Q4/Q5 三条红线门禁的严格度被降低。

**典型表现：**

| 表现 | 示例 |
|---|---|
| 阈值放松 | "100% 被拒" 改成 "≥ 90% 被拒" |
| 用例减少 | 伪造证据注入用例从 3 类减到 1 类 |
| 断言弱化 | `assert rejected` 改成 `assert result is not None` |
| 跳过用例 | `@pytest.mark.skip` / `xfail` |
| 抽样替代 | 越界测试从"全部绕过手法"改成"抽查 3 个" |
| 测试对象替换 | 测一个简化版函数而非真实路径 |

**检测方法：**

```bash
# 1. 检查是否有被跳过的测试
grep -rn "pytest.mark.skip\|pytest.mark.xfail\|@Ignore\|t.Skip" tests/

# 2. 检查门禁测试的历史变更
git log -p -- tests/antifantasy/ tests/scopekernel/
# 关注：断言是否被削弱、用例是否被删除、阈值是否被放宽

# 3. 检查断言质量
grep -rn "assert" tests/scopekernel/ | grep -v "=="
# 弱断言（如 assert result）需人工确认

# 4. 检查 mock 边界
grep -rn "mock\|patch\|MagicMock" tests/
# 确认没有被 mock 的"被验证对象"
```

**严重度：** 🔴 **P0**（红线是项目的存在前提）

---

### P3 · 安全机制绕过

**定义：** 引入了绕过 Evidence Ledger、Scope Kernel、Privacy Gateway、Termination Arbiter 的代码路径。

**典型表现：**

| 表现 | 定位 |
|---|---|
| 存在不经闸门产出 CONFIRMED 的路径 | 违反 R4 |
| 越界时"跳过该请求"而非熔断 | 违反 R8 |
| 提供关闭 Privacy Gateway 的 UI 开关 | 违反 R7 |
| 存在 agent 自行终止会话的路径 | 违反 R6 |
| 用 `except: pass` 吞掉安全异常 | 违反 P-4（fail-closed） |
| 新增"临时"绕过标记 | `# TODO: bypass scope check for testing` |

**检测方法：**

```bash
# 1. 搜索直接构造 CONFIRMED 的代码
grep -rn "status.*=.*CONFIRMED\|status.*=.*'confirmed'" --include="*.py" --include="*.go" .

# 2. 搜索自行终止路径
grep -rn "sys.exit\|os._exit\|SystemExit\|raise SystemExit\|session.close\|return.*TERMINATED" agents/

# 3. 搜索异常吞掉
grep -rn "except.*:\s*$\|except.*pass\|catch.*{\s*}" --include="*.py" --include="*.go" .

# 4. 搜索绕过标记
grep -rn "TODO.*bypass\|FIXME.*skip\|HACK.*disable\|temporarily" --include="*.py" --include="*.go" .

# 5. 检查 Gateway 是否有禁用开关
grep -rn "gateway.*disable\|privacy.*off\|disable_privacy" web/src/ core/
# UI 中不应存在该开关
```

**严重度：** 🔴 **P0**（直接摧毁核心价值）

### P4 · 违反核心原则

**定义：** 违反五条开发原则（P-1 可靠优先 / P-2 确定性优先 / P-3 证据先于结论 / P-4 失败即熔断 / P-5 可复现）。

**典型表现：**

| 表现 | 违反 |
|---|---|
| 新增 LLM 调用做本可确定性实现的事（如解析、格式转换） | P-2 |
| 存在不经账本的 finding 路径 | P-3 |
| 异常被吞掉、失败后继续执行 | P-4 |
| 引入随机种子未固定、时间依赖未消除 | P-5 |
| 用 LLM 拼命令行 | P-2 + R5 |
| 长程规划交给 LLM 逐步决策（而非确定性规划器） | P-2 |

**检测方法：**

```bash
# 1. 枚举所有 LLM 调用点
grep -rn "llm\|completion\|chat\|generate\|invoke_model\|call_model" --include="*.py" agents/ | grep -v test
# 逐个确认：为什么不用确定性代码？

# 2. 检查随机性与时间依赖
grep -rn "random\.\|uuid4\|datetime.now()\|time.time()" --include="*.py" --include="*.go" core/ agents/
# 确定性路径中不应出现（uuid7 与审计时间戳除外）

# 3. 检查失败是否向上传播
# 人工审阅：关键路径的 error handling 是否 fail-closed
```

**严重度：** 🟠 **P1**（P-2/P-3 违反按 P0 处理）

### P5 · 确定性破坏

**定义：** 本应字节级可复现的路径引入了不确定性。

**典型表现：**

| 表现 | 影响 |
|---|---|
| map/dict 迭代顺序影响输出 | 相同输入产出不同结果 |
| 浮点累加顺序不固定 | 结果不稳定 |
| 未固定随机种子 | 测试不可复现 |
| 未固定 LLM temperature | 评测结果不可复现 |
| 并行任务的结果顺序未排序 | 输出顺序随机 |

**检测方法：**

```bash
# 1. 检查确定性测试是否仍存在且有效
ls tests/ | grep -i determin
# 确认测试断言是"字节级一致"而非"近似相等"

# 2. 检查 map/dict 迭代
grep -rn "for.*range.*map\[" --include="*.go" .
# Go 中 map 迭代顺序随机，若影响输出需排序

# 3. 实际验证（最可靠）
# 同一输入运行 3 次，对比输出哈希
```

**严重度：** 🟠 **P1**（确定性是"可复现性"的基础，而可复现性是 P-5 原则）

### P6 · 界面功能简化

**定义：** 三个核心视图（证据链 / 光圈上下文 / 冲突矩阵）被简化或省略。违反 R9。

**典型表现：**

| 表现 | 判定 |
|---|---|
| 三个视图缺任意一个 | 🔴 直接违反 R9 |
| 证据链只显示列表，不显示树形与交叉引用 | 🔴 功能简化 |
| 光圈视图不显示 `truncated_dimensions`（省略维度） | 🔴 丢失关键信息 |
| 冲突矩阵退化成列表 | 🔴 二维结构丢失 |
| 只有配色/布局粗糙 | 🟢 允许（视觉简化） |

**检测方法：**

```bash
# 1. 确认三个视图目录存在
ls web/src/views/evidence web/src/views/aperture web/src/views/conflicts

# 2. 检查关键信息字段是否渲染
grep -rn "truncated_dimensions\|selection_reasons" web/src/views/aperture/
grep -rn "CONTRADICTS\|quadrant" web/src/views/conflicts/
grep -rn "assertions\|evidence_id\|exec_id" web/src/views/evidence/

# 3. 打开页面实际查看（需提供截图）
```

**严重度：** 🔴 **P0**（省略 = 放弃项目差异化）

### P7 · 范围蔓延

**定义：** 做了 `06` §11 明确拒绝的功能，或超出当前迭代范围的功能。

**明确拒绝清单（`06` §11）：**

| 拒绝项 |
|---|
| SaaS 化在线服务 |
| 浏览器插件 |
| 移动 App |
| Electron 桌面端 |
| 多租户 SaaS 计费 |
| 为第三方 UI 提供稳定 API 承诺 |
| 内建 IM 集成（Slack/钉钉等） |

**其他越界表现：**
- 提前实现后续迭代的功能（如 I1 就写 M7 融合）
- 引入当前迭代不需要的抽象层
- 做"顺手"的功能增强

**检测方法：**

```bash
# 1. 对照 06 §11 拒绝清单，检查仓库中是否有相关目录/依赖
ls web/ | grep -i "extension\|plugin"
cat package.json | grep -i "electron"

# 2. 对照当前迭代的交付物清单（04 §4），检查是否有超范围文件
# 人工：新增文件是否都能对应当前迭代的交付物？

# 3. 检查依赖新增
git diff HEAD~N -- go.mod requirements.txt package.json
```

**严重度：** 🟡 **P2**（记录并要求删除越界产物；若涉及拒绝清单则 🟠 P1）

### P8 · 阶段跳越

**定义：** 未达阶段门禁就开始了下一阶段的工作。违反 R10。

**门禁清单（`04`）：**

| 阶段 | 门禁（全部满足） |
|---|---|
| P0 | 24h 无崩溃 · 伪造证据 100% 被拒 · 越界 100% fail-closed · 隐私抓包零泄漏 · 预算耗尽必熔断 |
| P1 | 实体召回率 ≥95% · 超预算装配必然拒绝 |
| P2 | 公开基准可复现分数 · 业务逻辑首个可复现数字 |
| P3 | 143h 无崩溃 · 成本降 ≥60% |

**检测方法：**

```bash
# 1. 确认当前阶段的门禁是否全部通过
# 逐项准备门禁证据（测试命令 + 原始输出），不接受记忆复述

# 2. 检查是否已有下一阶段的文件
ls agents/fusion/ agents/intent/ 2>/dev/null
# 若 P0/P1 未完成却已有这些目录，即为跳越

# 3. 检查稳定性测试记录
ls tests/stability/ && cat tests/stability/last_run.json
# 24h 测试（P0）与 143h 测试（P3）是否有真实记录
```

**严重度：** 🔴 **P0**（对齐 AIxCC 教训：地基不稳，上层全废）

### P9 · 文档失真

**定义：** DoD 达成报告与实际情况不符；或活文档未按规则回填。

**典型表现：**

| 表现 | 判定 |
|---|---|
| 报告写"达成"，实际未达成 | 🔴 虚报 |
| 未达成但未说明根因 | 🔴 违反 `09` §10 |
| 部分达成未标注 | 🟠 不完整 |
| `04` 的活文档部分未回填 | 🟡 流程缺失 |
| `06` 演进记录未更新 | 🟡 流程缺失 |
| 新增文档未登记到 `README` §2/§3 | 🟡 流程缺失 |

**检测方法：**

```bash
# 1. 逐条核对 DoD
# 打开 04 的目标迭代，读到 DoD，然后逐条独立验证（不要凭记忆，要跑命令看输出）

# 2. 检查活文档是否更新
git log --oneline -- docs/04-开发总纲-阶段规划与依赖.md
# 若代码有大量提交但文档无更新，说明未回填

# 3. 检查新增文档是否登记
git status --short docs/
# 新增的 md 文件是否已出现在 README §2
```

**严重度：** 🔴 **P0**（虚报）／ 🟠 **P1**（未说明）／ 🟡 **P2**（流程缺失）

**定义：** 当前迭代声明的交付物未全部产出（含「前端交付物」）。

**检测方法：**

# 1. 打开 04 §4 的目标迭代，列出全部交付物（含前端交付物行）

## 4. 严重度分级与处置

| 级别 | 图标 | 含义 | 处置 |
|---|---|---|---|
| **阻断级** | 🔴 **P0** | 破坏项目根基（契约、红线、安全机制、核心视图、门禁） | **立即停止开发；产出必须回滚；修复后重新自检** |
| **必修级** | 🟠 **P1** | 违反原则或缺失交付物，不阻断但不得进入下一迭代 | **本迭代内修复；下一迭代启动前重新自检** |
| **记录级** | 🟡 **P2** | 流程或规范问题，不影响功能正确性 | 登记到问题清单；可延后处理 |

**处置规则：**

| 情形 | 结论 |
|---|---|
| 出现任意 🔴 P0 | **判定为"必须回滚"** —— 不得继续开发新功能 |
| 出现 🔴 但已确认修复并重新验证 | 可降级为 🟠 |
| 仅 🟠 P1 | **判定为"需修正"** —— 修复后可继续 |
| 仅 🟡 P2 | **判定为"可继续"** —— 登记待办 |
| 全部通过 | **判定为"可继续"**，并确认是否满足进入下一阶段的条件 |

## 5. 自检报告模板

**每个迭代结束时必须产出此报告，作为交付物的一部分。**

**迭代**：I__

**自检依据**：05 契约 / 04 §4 的 DoD / 09 的十条红线 / 02 §2 设计原则

## 一、DoD 达成核对

| # | DoD 条目 | 状态 | 验证命令 | 原始输出（摘要） | 判定 |

## 6. 自检时机

| 时机 | 严格度 | 重点 |
|---|---|---|
| **每个迭代末** | 完整自检 | DoD 达成（附证据）、红线专项核查、交付物完整性 |
| **阶段门禁前（P0/P1/P2/P3 末）** | **最严** | 门禁逐项验证 + 稳定性测试原始记录 + 对照 `07` 复查威胁覆盖 |
| **引入新载体 / 新攻击面时** | 常规 | 对照 `07-threat-model.md` 复查威胁覆盖 |
| **修改了安全相关代码后** | 立即 | 局部自检 P2/P3/P4（红线放宽、安全绕过、原则违背） |

**两个强制时点：**

| # | 时点 | 要问自己什么 |
|---|---|---|
| **1** | **写完测试之后、跑测试之前** | 读一遍测试代码：这些断言真的在验证功能吗？还是只验证了函数被调用过？ |
| **2** | **提交之前** | 跑一次 §3 的 P1 / P2 / P3 检测命令。这三类最容易在无意识中发生 |

**建议：每完成一个模块（不必等到迭代末）就做一次轻量自检**，聚焦 P1 契约漂移与 P3 安全绕过。过程发现的返工成本远低于末期发现。

---

## 7. 自检的三条自我约束

**为避免自检失真：**

| # | 约束 | 原因 |
|---|---|---|
| **1** | **不以"代码看起来合理"代替命令验证** | 跑偏的代码往往看起来很合理，这正是它危险的地方 |
| **2** | **不因"改动很小"就跳过红线核查** | 契约漂移与安全绕过往往就藏在一行改动里 |
| **3** | **无法验证的项必须显式声明** | 不能让"没查"伪装成"没问题"。宁可写"仅人工判断"，也不要写"通过" |

## 8. 把检查固化为 CI（终极方案）

**本文件的长期目标是让自己变得不必要** —— 检查项一旦写进 CI 门禁，就无法自欺。

| 检查项 | 当前方式 | 应固化为 |
|---|---|---|
| P1 契约漂移 | 人工 diff | CI 校验实现与 `05` 契约的一致性（Protobuf 生成物比对） |
| P2 红线放宽 | 人工审阅测试 | CI 检查测试变更：断言不得减少、阈值不得放宽、不得新增 skip |
| P3 安全绕过 | grep | CI 静态规则：禁止 `= CONFIRMED` 直接赋值、禁止 `except: pass`、禁止绕过 Gateway |
| P7 范围蔓延 | 人工对照 | CI 检查依赖白名单与目录白名单 |
| P10 交付物缺失 | 人工清单 | CI 检查交付物文件是否存在 |

**判断标准：如果一个检查项连续两个迭代都靠人工完成，它就应该被写成 CI 门禁。**

**当前 CI 门禁清单见 `04-开发总纲` §6（Q1–Q14）。** 考虑把上表的自动化检查补充为 Q15+。
