# M3 · 光圈控制（L2）★核心创新

> 模块编号：M3 ｜ 层：L2 Aperture Control ｜ 建议语言：**Python**
> 迭代：I5 ｜ 上游：M2 ｜ 下游：M5

---

## 1. 职责

给定「当前任务 + 当前假设」，从心智地图中**投影出最小充分上下文**，并保证不超出 token 预算。

一句话：**记忆在图里，上下文只是焦点的投影 —— 信息不因离开上下文而丢失。**

---

## 2. 要解决的问题

调研记录的 D4（上下文失忆），实测表现：

> agent 发现了一个隐藏 API 参数，随后被另一个端点分心，**20 步之后完全遗忘了这个线索**。它缺少人类渗透测试员在笔记中维护的持久结构化心智地图。

根因：现有项目把**上下文窗口当记忆用**。上下文满了就只能丢弃，丢弃即永久丢失。

M3 的解法：**上下文不承载记忆，只承载"当前焦点的投影"。** 需要时可重新投影。

---

## 3. 边界

### 3.1 本模块做

| # | 职责 |
|---|---|
| R1 | Autofocus：从任务与假设定位焦点 |
| R2 | Aperture Selector：确定光圈档位（信息密度） |
| R3 | Context Assembly：装配 ContextBundle 并渲染 |
| R4 | 预算约束：超预算必须拒绝，自动降档重试 |
| R5 | 可审计性：记录"为什么选这些实体" |

### 3.2 本模块不做

| # | 不做 | 归属 |
|---|---|---|
| N1 | 不做图遍历实现（调用 M2 `Project`） | M2 |
| N2 | 不做预算记账（向 M6 Governor 预扣） | M6 |
| N3 | 不判断实体真伪（消费 M4 的状态） | M4 |
| N4 | **不允许截断装配结果** | — |

**N4 的理由：** 截断会产生"信息看起来完整但实际缺失"的静默错误——这是 D1 幻觉式成功的温床。超预算时必须显式失败并降档重选。

## 4. 内部设计

### 4.1 光圈模型

| 档位 | 语义 | max_hops | max_entities | depth_per_entity | 适用任务 |
|---|---|---|---|---|---|
| **f/1.4** | 大孔径：宽而浅 | 1 | 200 | 1（仅关键属性） | 攻击面总览、初始侦察规划 |
| **f/4** | 中孔径：平衡 | 2 | 60 | 2 | 常规漏洞分析 |
| **f/16** | 小孔径：窄而深 | 3 | 10 | 5（含原始输出片段） | 单点利用、PoC 编写 |

**物理约束（恒定曝光）：** 光圈开大必须别处关小。系统维护全局预算 B，装配必须满足：

```
Σ(entity_i × depth_weight_i × hop_weight_i) ≤ B
```

**这不是优化目标，是硬约束。** 它直接消解 D13（把产出量当价值）——给 LLM 的信息总量有上限，必须主动取舍。

### 4.2 Autofocus 算法

```
输入：task.objective（任务目标）+ 当前 hypothesis（可选）
输出：focal_point（焦点实体集）+ 各维度的关注权重

步骤：
1. 抽取实体引用
   · 从 task.objective 与 hypothesis 中识别已命名的实体（服务名/URL/凭据类型/资产地址）
   · 与地图做精确匹配 + 模糊匹配，得到种子实体集 S₀

2. 图上游走
   · 从 S₀ 出发，按当前档位的 max_hops 游走，收集候选集 S₁
   · 沿类型化关系游走时，关系类型有权重（见 4.3）

3. 相关度排序
   · score(e) = w_ref · is_direct_ref(e)
              + w_hop · hop_decay(distance(e, S₀))
              + w_rel · max(relation_weight(path))
              + w_conf · e.confidence
              + w_rec · recency(e.observed_at)
              + w_conflict · is_in_conflict(e)      ← 冲突实体加分
   · 默认权重：w_ref=1.0, w_hop=0.5, w_rel=0.3, w_conf=0.4, w_rec=0.2, w_conflict=0.6

4. 证据强度过滤
   · CONFIRMED 状态的缺陷实体优先
   · Hypothesis 实体仅在高置信度实体数量不足 max_entities 时才注入

5. 按预算截断
   · 按 score 降序取，累加估算 token，直到触及 budget × 0.95
   · 若无法装入（最小实体集仍超预算）→ 返回 APERTURE_OVER_BUDGET
```

### 4.3 关系权重表

| 关系类型 | 权重 | 理由 |
|---|---|---|
| `EXPLOITED_BY` | 1.0 | 直接关联利用 |
| `AUTHENTICATES_TO` | 0.9 | 凭据是链式攻击的关键（直击 D6 跨阶段传递失败） |
| `CONTRADICTS` | 0.85 | **冲突是最高价值信号** |
| `REQUIRES` / `ENABLES` | 0.8 | 攻击链前置/后置条件 |
| `EXPOSES` | 0.7 | 攻击面 |
| `RUNS_ON` / `RESOLVES_TO` | 0.5 | 基础设施关联 |
| `BELONGS_TO` | 0.4 | 归属 |
| `PRECEDED_BY` | 0.3 | 时序 |
| `CORROBORATES` | 0.6 | 多源印证 |

### 4.4 Context Assembly 输出结构

装配结果不是纯文本，而是**结构化 ContextBundle**（见契约 §4.1），渲染时按区块组织：

```
┌─ 焦点声明 ─────────────────────────────┐
│ 当前任务：<objective>                   │
│ 焦点：<focal_point>                     │
└────────────────────────────────────────┘
┌─ 高相关实体（按 score 降序）─────────────┐
│ [svc_xxx] 443/tcp nginx 1.24.0          │
│   └ 关系：EXPOSES → [ept_yyy] /api/v2   │
│   └ 证据：ev_zzz (✅ CONFIRMED)          │
└────────────────────────────────────────┘
┌─ 冲突提示（若有）───────────────────────┐
│ ⚠ svc_xxx 版本存在冲突：白盒 1.24.0 /   │
│   黑盒 1.22.1 —— 建议优先核实            │
└────────────────────────────────────────┘
┌─ 已省略维度（必须显式声明）──────────────┐
│ 因预算省略：TIMELINE 全量、ASSET 属性深度 │
└────────────────────────────────────────┘
```

**硬要求：** 被省略的维度必须写入 `truncated_dimensions` 并在渲染中出现。**不允许静默省略**——让 LLM 知道"它不知道什么"，比让它误以为信息完整更安全。

### 4.5 Token 估算

| 内容 | 估算方式 |
|---|---|
| 实体 | 属性名+值字符数 / 3.5（保守系数） |
| 关系 | 固定 12 token |
| 证据摘要 | 固定 30 token + 断言文本长度 |
| 结构开销 | 每实体 +8 token |

估算必须**偏保守**（宁可低估预算也不可超支）。装配后如实际 token 超预算，视为缺陷（估算器需修正），不得运行时纠正。

## 6. 测试要求

| 类别 | 要求 | 门禁 |
|---|---|---|
| **召回率** | 构造 100 组"任务 A 发现的实体，任务 B 需要用到"的用例，召回率 **≥ 95%** | Q1 |
| 预算约束 | 100% 装配结果 `estimated_tokens ≤ budget_tokens`；超预算必然拒绝 | Q1 |
| 降档重试 | 超预算后自动降档能成功装配（构造超预算用例） | Q1 |
| 确定性 | 相同输入装配结果一致（排序稳定性） | Q6 |
| 省略显式性 | 被省略维度 100% 出现在 `truncated_dimensions` | Q1 |
| 审计性 | `selection_reasons` 能被还原为打分依据 | Q1 |
| 对比基线 | 相比"全量注入"，token 量降 ≥ 70% 且任务成功率不降 | — |

**召回率测试的设计要点：** 用例必须真实构造跨任务依赖链（如任务 A 的 httpx 发现 `/api/v2`、任务 B 的 nuclei 需要该端点作为输入），而非人工指定焦点。这是检验 M3 是否真正解决 D4 的关键。

## 7. 验收标准（DoD）

- [ ] 三档光圈 + 连续调节可用，档位切换影响实测 token 量与成功率
- [ ] **跨任务实体召回率 ≥ 95%**
- [ ] 超预算 100% 拒绝并降档，无截断路径
- [ ] 省略维度 100% 显式声明
- [ ] `selection_reasons` 完整可审计
- [ ] 相比全量注入基线：token 降 ≥ 70%，成功率不降
- [ ] 提供 `aperture=off`（全量注入）调试开关，且该模式下功能仍正确

## 8. 风险与降级

| 风险 | 缓解 |
|---|---|
| 召回率不足（最严重） | 专设回归测试；关系权重可调；提供 `aperture=off` 降级；若持续不达标则提高默认档位（牺牲成本保正确性） |
| Token 估算偏差导致实际超预算 | 保守系数；上线前用真实数据校准；超支视为缺陷而非运行时修正 |
| 排序权重难以调优 | 权重外置为配置，支持 A/B 对比；用召回率与成功率为目标函数 |
| 冲突实体过多挤占预算 | 冲突实体设数量上限（默认 5），超出部分只给 ID 摘要 |
| Autofocus 依赖任务描述的实体命名 | 要求 Planner（M5）在生成任务时输出结构化 `target_entity_hints`，而非仅自然语言 |
