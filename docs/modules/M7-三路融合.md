# M7 · 三路融合（Trichromatic Fusion）

> 模块编号：M7 ｜ 层：跨层（L1 写入 + L0 执行） ｜ 建议语言：**Python（白盒）+ Rust/Go（二进制）**
> 迭代：I8 ｜ 上游：M1、M2、M5 ｜ 下游：M8

---

## 1. 职责

用**三种独立观测手段**（黑盒运行时 / 白盒源码 / 二进制）观测同一目标，全部写入同一心智地图，并输出**冲突矩阵**。

一句话：**冲突不是需要消除的噪声，而是最高价值的信号。**

---

## 2. 行业空白（立项依据 G4）

调研 39+ 个开源项目后的结论：

| 范式 | 代表 | 局限 |
|---|---|---|
| 黑盒 agent | Strix、HexStrike、PentAGI | 不做代码级分析，无法定位根因 |
| 白盒分析 | **VulnHuntr** | **仅支持 Python**；只有 CLI，无 agent 编排；无法验证可利用性 |
| 二进制分析 | **VulHunt**（Binarly） | 完全独立，不与其他观测交互 |

**没有任何一个项目统一了三路观测。** 这是 Aletheia 的第二个"第一"。

---

## 3. 边界

### 3.1 本模块做

| # | 职责 |
|---|---|
| R1 | 白盒观测器：源码 → 调用链 → 缺陷定位 |
| R2 | 二进制观测器：无源码目标的静态分析 |
| R3 | 三路结果统一写入心智地图（带 `SourceKind` 标记） |
| R4 | 冲突检测与 `CONTRADICTS` 关系落图 |
| R5 | 冲突矩阵生成与四象限解读 |
| R6 | 冲突驱动的下游任务派生 |

### 3.2 本模块不做

| # | 不做 | 归属 |
|---|---|---|
| N1 | **不维护独立存储**（全部写入 M2 的单一图） | M2 |
| N2 | **不强行合并冲突**（保留多版本） | — |
| N3 | 不判定漏洞成立（写入的是 DEFECT 实体，状态由 M4 驱动） | M4 |
| N4 | 不重实现 SAST 引擎（可复用 Semgrep/CodeQL 作为数据源） | — |

**N4 的说明：** 目标不是重写静态分析器，而是**把静态分析结果纳入 agent 的证据体系**。复用成熟引擎（Semgrep、CodeQL、tree-sitter）做解析，本模块负责语义映射与融合。

## 4. 内部设计

### 4.1 三路观测器

```
        ┌─────────────────────────────────────┐
        │      Mental Map（M2，唯一真源）       │
        └───▲──────────────▲──────────────▲───┘
            │              │              │
   ┌────────┴───┐  ┌───────┴────┐  ┌──────┴──────┐
   │ 黑盒观测器  │  │ 白盒观测器  │  │ 二进制观测器 │
   │ （M1 复用）  │  │  （本模块）  │  │  （本模块）  │
   ├────────────┤  ├────────────┤  ├─────────────┤
   │ 端口/服务   │  │ 调用链      │  │ 反汇编       │
   │ 端点/响应   │  │ 污点传播    │  │ 符号/字符串   │
   │ 认证行为    │  │ 依赖漏洞    │  │ 固件/内存布局 │
   │ 实际可利用性│  │ 根因位置    │  │ 硬编码凭据    │
   └────────────┘  └────────────┘  └─────────────┘
   SourceKind:      SourceKind:      SourceKind:
   ACTIVE_SCAN      WHITEBOX_SOURCE  BINARY
```

### 4.2 白盒观测器

**能力对标 VulnHuntr**（其发现 12+ 大型开源项目的 0day：gpt_academic LFI/XSS、ComfyUI XSS、Langflow RCE/IDOR、FastChat SSRF、Ragflow RCE、LLaVA SSRF 等）。

| 能力 | 实现 |
|---|---|
| 调用链追踪 | 从远程输入源（HTTP handler / CLI / 反序列化入口）追踪到危险汇聚点 |
| 污点传播 | 复用成熟引擎（Semgrep / CodeQL）作为底层，本模块做语义映射 |
| 语言支持 | **不限制 Python** —— 用 tree-sitter 做多语言解析（这是对 VulnHuntr 边界的补强） |
| 依赖漏洞 | 解析依赖清单 + 版本 → 匹配已知漏洞库 |
| 输出 | DEFECT 实体（含 `location`：文件:行号） + 调用链作为 PATH 实体 |

**关键差异化的技术点：** 白盒结果写入地图后，**可被黑盒任务消费**。例如白盒定位到 `/api/v2/export` 存在参数注入，黑盒 Exploiter 会收到这个端点作为 `target_entity_hints`——这正是"三路融合"的实用价值。

### 4.3 二进制观测器

**能力对标 VulHunt**（无需源码即可分析 POSIX 可执行文件与 UEFI 固件）。

| 能力 | 技术 |
|---|---|
| 反汇编与控制流 | Ghidra headless / radare2 / Capstone |
| 符号与字符串 | 硬编码凭据、内部 URL、调试信息 |
| 内存安全线索 | 危险函数调用（`strcpy`/`sprintf`）、栈保护状态 |
| 依赖与版本 | 嵌入式库版本指纹 → 漏洞匹配 |
| 固件分析 | binwalk 解包 + 文件系统提取 |

**为什么需要这一路：** 真实渗透中大量目标是**无源码**的（闭源设备、IoT、固件）。白盒工具在此完全失明。

### 4.4 冲突矩阵（核心产出）

| 黑盒结果 | 白盒结果 | 解读 | 优先级 | 动作 |
|---|---|---|---|---|
| 可利用 | 有缺陷 | **双源确认** | 高 | 直接进 Candidate，复现后 Confirmed |
| **打不通** | **有缺陷** | **利用条件未满足 / 环境差异 / 需前置认证** | **最高** | **深挖前置条件 —— 可能是链式漏洞的第一环** |
| 可利用 | 无缺陷 | 配置/环境类问题，或白盒漏检 | 中 | 交叉复核，可能是白盒盲区 |
| 打不通 | 无缺陷 | 可能确实安全 | 低 | 降优先级 |

**最高价值象限是第二行。** 白盒说这里有洞、黑盒打不通——这对纯黑盒 agent 是盲区（它只知道"打不通"），对纯白盒工具也无意义（它不验证可利用性）。**只有融合才能识别出"这是链式漏洞的第一环"。**

依据（调研 D6）：链式漏洞成功率仅约 **16%**，agent 常卡在无法把侦察阶段的发现传递到利用阶段。冲突矩阵是把"打不通"从失败转化为线索的机制。

### 4.5 冲突落图

```python
# 冲突不合并，而是以 CONTRADICTS 关系显式落图
relation = Relation(
    from_entity=blackbox_defect_id,
    to_entity=whitebox_defect_id,
    type=RelationType.CONTRADICTS,
    attributes={"quadrant": "UNREACHABLE_BUT_FLAWED"},
    confidence=1.0,
)
```

M3 光圈控制在投影时给 `CONTRADICTS` 关系**高权重（0.85）**，且冲突实体会被优先呈现。M5 据此派生深挖任务。

## 6. 测试要求

| 类别 | 要求 |
|---|---|
| 白盒能力对标 | 在 VulnHuntr 公开的 0day 案例（如 Langflow RCE、FastChat SSRF）上验证调用链深度不低于其水平 |
| 多语言 | 至少覆盖 Python / Java / Go / JavaScript（超越 VulnHuntr 的 Python-only） |
| 二进制能力对标 | 在无源码的 POSIX 可执行文件上检出硬编码凭据与危险函数 |
| 冲突检测 | 构造"白盒有缺陷 + 黑盒打不通"场景，必须生成 `CONTRADICTS` 关系 |
| 冲突驱动 | 该象限的发现能被 M5 消费并派生出深挖任务 |
| 单源写入 | 三路全部写入 M2，无独立存储（静态检查） |
| 不合并 | 冲突保留多版本，投影时全部可见 |

## 8. 风险与降级

| 风险 | 缓解 |
|---|---|
| 白盒需要源码，目标常无源码 | 三路不是必须全有：单路可用时降级为单路模式，报告中标注观测覆盖度 |
| 二进制分析误报率高 | 二进制发现默认 `confidence < 0.6`，需黑盒验证才能升 CANDIDATE |
| 冲突过多导致噪声 | 冲突需过阈值（两侧 confidence 均 > 0.5）才落图；数量上限 |
| 静态分析工具集成成本 | 复用成熟引擎（Semgrep/CodeQL/Ghidra），不自研 |
| 多语言解析质量不均 | 按语言分别统计覆盖率并公开；优先支持目标常见语言 |

## 9. 观测覆盖度声明（必须写入报告）

三路观测不是总能齐全。报告必须显式声明本次运行的观测覆盖度：

```
观测覆盖度：
  ✅ 黑盒（运行时）    —— 完整
  ✅ 白盒（源码）      —— 覆盖 3 个组件，1 个组件仅二进制
  ⚠️ 二进制            —— 仅覆盖 2 个可执行文件
  ⚠️ 契约（Intent）    —— 无 OpenAPI，仅流量启发式
```

**理由：** 30% 的目标永远拿不到源码，把"用了三路"当作默认假设会产生过度自信（D13）。**声明覆盖度是诚实的必要条件。**
