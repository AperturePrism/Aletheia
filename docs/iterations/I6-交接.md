### 为什么刻意把"确定性骨架"与"LLM 接线"分开

M5 §2 的核心设计决策是**不让 LLM 做长程规划**。这个决策的价值恰恰
体现在"确定性部分能被独立验证"上：

- `NextReady` 的确定性、拓扑正确性、资源约束、关键路径 —— 全部可
  离线、可重复、可静态检查地验证；
- Agent 池涉及真实模型调用（成本、不确定性、凭据），验证方式完全不同。

把它们混在一个提交里，会让"零 LLM"这条契约约束无法被清晰断言。
**因此先交付并锁死骨架，再接线 LLM。** 这也是 `TestNoLLMClientInPackage`
能作为静态检查生效的前提。

> （除熔断外）。任何自行终止路径都是 P0 缺陷。

### 建议的第一步动作

I7 的 `TerminationService` 与 M5 的熔断器是**互补的两条终止路径**，
建议先读 `docs/modules/M4` §5 与 `modules/M5` §4.4，理清：

- 熔断 = 系统自动（预算/幻觉/越界）；
- `RequestTermination` = agent 申请 + Arbiter 独立校验（可拒）。

两者都不允许 agent 自行终止。`orchestrate` 包的 `ActionTerminateSession`
是**熔断标记**，最终终止动作须由 M4 的 Arbiter 执行。

### 接手方注意事项

1. **不要削弱 `TestNoLLMClientInPackage`** —— 见 `I5-交接.md` §7 第 1 条。
2. **`AssignResult` 的 FAILED 必须带 FailureRecord** —— 这是 Refiner 的
   输入契约。接线 Agent 池时，agent 上报失败必须带结构化失败类型，
   不能只报"失败了"。
3. **检查点是内存态** —— `CheckpointStore` 不持久化。跨进程恢复需要
   接 M2 的图版本（`GraphVersion` 字段已留位）与 M6 的预算快照
   （`BudgetHash` 字段已留位）。这是 I6 的 `Checkpoint` RPC 目前
   `graph_version` / `budget_snapshot_hash` 为空的原因。
