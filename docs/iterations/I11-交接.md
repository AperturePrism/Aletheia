## 6. 已知缺口与风险

| 缺口 | 影响 | 何时必须解决 | 阻塞谁 |
|---|---|---|---|
| 公开基准适配器（T9.3–T9.6） | 无法产出与行业基线可比的分数 | 需 CTFd / 容器编排 / 靶场 API | 阻塞 P2 阶段门禁"公开基准分数产出" |
| 自建靶场一键起停（T9.2/T9.7/T9.8） | 无法端到端跑评测 | 需 docker | 阻塞 P2 阶段门禁 |
| 一键复跑脚本 + CI 集成（T9.12） | 第三方复跑需手工步骤 | 依赖上述两项 | — |

### 交付边界的理由

M9 §5.1 的适配器清单全部需要外部环境（CyBench 需 CTFd、CVE-Bench 需
容器编排、HTB 需靶场 API）。因此本包交付**框架与契约 + 指标计算 +
报告生成** —— 全部可**离线完整测试**。

这与 I8（M7 的融合逻辑与引擎适配器分离）是同一策略：
最需要保证正确性的部分是**判定与统计口径**，而那部分不该依赖
外部环境的可用性。

### ★ P2 阶段门禁的当前状态

`04` §4 的 **P2 阶段门禁是「公开基准分数产出 + 业务逻辑数字产出」**：

* **业务逻辑数字**：I10 已给出统计口径与判定逻辑的可复现性；
  **真实能力数字待执行侧**（见 `I10-交接.md` §6）。
* **公开基准分数**：本迭代交付了计算框架；**分数本身待适配器**。

**因此 P2 阶段门禁尚未通过** —— 这是外部环境依赖，不是实现缺口。

**在无外部资源时**，I12 可推进的确定性部分：

1. **熔断器补齐 2/8 类**（"总运行时长上限"与"单任务 token 超预算"）
   —— `orchestrate.CircuitState` 已留位；
2. **检查点持久化**（I6 的 `Checkpoint` RPC 目前 `graph_version` 与
   `budget_snapshot_hash` 为空）；
3. **G-4 独立复现**（T4.9）的**框架部分**（执行需 docker）。

### 接手方注意事项

1. **`failures` / `limitations` 是 `build_report` 的必填关键字参数**
   —— 这是 M9 §2.2 N3 与 §11 承诺 3 在 API 层面的强制，**不要加默认值**。
2. **`aggregate()` 不得加过滤参数** —— 有测试断言（`inspect.signature`）。
   M9 §10 明确"全部基准跑全量任务，不做筛选"。
3. **分母为 0 必须返回 None，不能填 0** —— 见 §5 的仅人工判断项。
4. **基线引用必须四项标注**，且 **87% 与 7% 必须同时收录** ——
   只收录 87% 就是在复现 M9 §3 的反面案例（有专门测试守护）。
5. **报告页的"调试"层是原始证据链**，不是"包含推测的报告层" ——
   后者在契约上不存在（05 §7.2 的 proto 里没有 HYPOTHESIS 字段）。
