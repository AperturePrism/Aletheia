## 6. 已知缺口与风险

| 缺口 | 影响 | 何时必须解决 | 阻塞谁 |
|---|---|---|---|
| `aperture=off` 调试开关（DoD⑦） | 无法快速对照"全量注入"行为 | I6 接线 Agent 池前（便于对照调试） | 不阻塞 |
| 召回率测试是合成图（非真实工具输出） | 真实图谱的召回表现可能不同 | 有真实会话数据后补端到端 | 不阻塞 |
| 图上游走依赖 M2 `Project` 的 maxEntities | 候选池被 M2 截断时可能漏掉远处线索 | 大规模会话实测后 | 不阻塞 |

**最严重的风险（M3 §8 首位）是召回率不足。** 本实现的三重保障：
① 专设 100 组回归测试；② 关系权重表可外置调整（`Options.Weights`）；
③ 候选池下限硬编码 200（`poolSize`），避免池子太小让远处线索进不来。

### 接手方注意事项

1. **`NextReady` 绝对不能引入 LLM** —— 契约硬约束（05 §6.2）。
   `orchestrate_test.go` 的 `TestNoLLMClientInPackage` 是静态检查，
   会扫描源码拒绝任何 LLM SDK 或网络调用。**不要把该测试改成运行时
   断言** —— 运行时测试无法发现"引了依赖但测试不走那条分支"。
2. **M2 §6 要求实体属性中的 `credential_ref` 是脱敏 token** ——
   M3 不二次脱敏（见 §5 R7 说明）。接线 Agent 池时须核对 M1→M2
   写入路径确实过 Gateway。
3. **`.venv` 的 python 路径**：`scripts/lint.sh` 会自动探测
   `.venv/Scripts/python.exe`（Windows）或 `.venv/bin/python`（POSIX）。
