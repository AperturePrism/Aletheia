## 3. 交付了什么

### 3.1 模型中立 Provider 与分级路由（DoD③）

`agents/src/aletheia/providers/provider.py`：

| 组件 | 作用 |
|---|---|
| `Provider` (Protocol) | 模型中立最小接口（D17：不暴露任何模型特有能力） |
| `OpenAICompatProvider` | OpenAI 兼容协议；429/网络错误有限指数退避；其它 HTTP 错误**不重试**（fail-closed） |
| `Usage` / `ChatResult` | 统一用量与结果；`reasoning_tokens` **单独记账**（降本分析的关键维度） |
| `CostLedger` | 按模型 / 按档位聚合；`LedgerEntry` 含 ts、model、tier、usage、latency |
| `Router` | 任务档位 → 模型 的**确定性**映射（零 LLM 参与，P-2） |
| `DEFAULT_TIER_EXTRAS` | 机械档关推理（deepseek/glm 认 `reasoning_effort=none`；flash-lite 认 `enable_thinking=false`） |

**一个设计取舍**：`reasoning_content` 不被当作产出，只取 `content`；
推理 token 单独记账。理由：推理过程是模型的中间态，把它当产出会让
"模型说了什么"与"模型想了什么"混为一谈，下游无法审计。

### 3.2 成本基准（DoD②，未达标但有完整归因）

`tests/i12/cost_benchmark.py` + `last_run.json`，**55 调用/配置，4 配置，共 220 次真实调用**
（2026-10-26）。

| 配置 | total tokens | reasoning 占比 | 降幅（token 口径） |
|---|---|---|---|
| 单一 glm-5.2（基线） | 25516 | **89%** | — |
| 分级路由 | 21153 | 79% | 17.1% |
| 优化路由（rank→deepseek） | 17167 | 83% | **32.72%（最佳）** |
| 分级 + 机械档关推理 | 19336 | 78% | 24.22% |

**为什么 60% 在 token 口径下结构性不可达**（四条原因链，均有数据）：

1. **推理 token 是绝对大头**（基线 89%）—— 渠道三个模型全部推理型；
2. **思考档是降幅天花板**：planning/analysis 占负载权重 27%，走重推理档且
   **推理保留是质量要求**（`04` §I6 决策①要求规划质量），机械档关推理
   不适用于此 —— 它们贡献基线约一半 token 且不可动；
3. 机械档关推理**确实生效**（探测：deepseek 关推理后 599 tokens/22 调用 ≈33/调用），
   但机械档基数本就不大，救不动总账；
4. `reasoning_effort=low` **实测无效**（371→372 tokens）。

**三条达成路径**（`tests/i12/README.md` §DoD② 的达成路径）：

| 路径 | 依据 | 依赖 |
|---|---|---|
| **货币口径核算** | token 降 33% + 轻档单价通常低 5–10 倍 → 货币降幅大概率 ≥60% | 渠道计费单价（外部数据） |
| **I13 微调小模型** | 高频子任务（parse/rank 占 73% 权重）的 token 大头是推理开销，非推理小模型是结构性解法 —— 正是 I13 降 ≥70% 的设计目标 | 训练基础设施 |
| 思考档换小模型 | 质量权衡，超出路由范畴 | I11 基准适配器（需 docker） |

**本基准同时是 I13 的动机证据** —— 它不是一次失败的优化，而是一次
"把天花板测出来了"的测量。

### 3.3 推理控制参数能力探测

`tests/i12/probe_reasoning_control.py` + `reasoning_probe.json`：
逐个渠道探测"怎样关掉推理"（三个模型认两种不同参数名）。
**为什么要探测**：不同渠道对推理控制的参数名不一致，写死一个会静默失效
（不发报错，只是推理照样跑，账本看起来"降本无效"）。

## 6. 已知缺口与风险

### 6.1 ★ DoD① 的 143h 结果缺失（必须补）

**现状**：`tests/stability/last_run/` 里的记录是 **2026-10-23 的本地短跑**，
不是 143h。143h 运行按记录于 2026-10-25T23:47Z 在 NAS 起跑、10-31 收口，
但**仓库中没有任何结果文件或判定记录**。

**为什么不能"口头上算通过"**：`04` §I12 DoD① 写的是"连续 143h 无崩溃"，
判据是崩溃数 0 / 探针全 ok / RSS 增长 < 5%。这三项都需要那次运行的
采样数据。没有数据就只能是"未验证"，不能是"通过"。

**补齐动作**（需要 NAS 访问）：

```bash
# 在 NAS 上取回结果目录
scp -r <nas>:/path/to/stability-run ./tests/stability/i12-143h/
# 判定三项判据，把结论写进 docs/decisions/ 与本节
```

**注意**：即便取回数据，也必须在**同一份代码**上跑 —— 若期间改过
`core/orchestrate` 或 `core/governor`，旧结果不再代表当前 HEAD。

### 6.2 DoD② 的口径决策（需要人签字）

`60%` 是**token 口径**还是**货币口径**，`04` 没有写明。两种口径结论相反：

* token 口径：**已证明不可达**（32.72% 是上限，不是还没优化）；
* 货币口径：**大概率可达**，但需要渠道单价数据（外部）。

**建议**：把 `04` §I12 DoD② 明确为"货币口径 ≥60%（token 口径 ≥30%）"，
并登记单价数据来源。**在此之前不应对外宣称任何降本数字** ——
用哪个口径都能得出"我们降了本"的结论，但只有说清口径才是可核对的。
