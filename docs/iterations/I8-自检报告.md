## 4. 自检的三个强制时点（`docs/10` §6）

### 时点 1：写完测试后、跑测试前 —— "这些断言真的在验证功能吗"

**★ 本迭代最重要的自检发现：对齐键的设计错误（由测试暴露）。**

初版把 `location` 纳入融合对齐键（照搬 `core/prism` 的
`载体|缺陷类型|位置`）。测试**立刻失败**：

```
E  AssertionError: assert 0 == 1
   # build_matrix 返回 0 个冲突（期望 1）
```

根因：三路对"位置"的表述天然不同：

```
黑盒：/api/v2/users          （运行时可见的入口）
白盒：app/views.py:42        （源码行号）
二进制：0x4012a0             （文件偏移）
```

含 location 的对齐键让三路对**同一缺陷**的观测永远无法对齐 ——
矩阵退化成三个互不相干的清单。

**我进一步实测了这个错误的真实后果**：用不同 location 写两条
DEFECT 观测到 M2，然后 `MergeBranch`：

```
merge: merged=true unresolved_conflicts=0
CONTRADICTS relations in graph: 0
```

**没有报错**，只是不工作。这是最危险的一类缺陷 —— 静默失效。

修正后（对齐键 = `载体|缺陷类型`）的端到端验证：

```
blackbox entity_key: 192.0.2.20|sqli     (location=/api/v2/users)
whitebox entity_key: 192.0.2.20|sqli     (location=app/views.py:42)
对齐: True
冲突数: 1 → 象限=UNREACHABLE_BUT_FLAWED 优先级=最高
派生任务: [最高] 深挖前置条件：sqli @ 192.0.2.20  hints=('192.0.2.20',)
```

代价是已知的**过度对齐**（同载体的同类缺陷会合并），已在
`Observation.entity_key` 的 docstring 详述并权衡说明。

**`test_static_observer_cannot_claim_exploitability` 的断言强度：**
它构造一个**试图**声称 `exploitability_verified=True` 的静态观测器，
断言基类强制改回 False。这条锁住的是矩阵赖以成立的不对称 ——
若静态观测能声称"已验证可利用"，四象限会全部塌缩成"双源确认"。

**`test_neither_quadrant_is_excluded` 的断言强度：**
断言"两路皆无"**不**进矩阵。若写反，低优先级的噪声会淹没高价值信号。

## 6. 仅人工判断的项（诚实声明）

| 项 | 为何无法自动化 | 判断依据 |
|---|---|---|
| 对齐键取舍是否合理 | 是设计判断（漏信号 vs 完全失效） | 实测确认含 location 会导致 `CONTRADICTS=0` 且无报错；权衡说明写在 docstring |
| 四象限视觉权重分配 | 视觉显著性无法自动断言 | 浏览器截图核对：最高价值象限紫罗兰 + 星标 + 独立高亮条 |

| 覆盖度三级判定是否够用 | 分级是设计判断 | 用 COMPLETE/PARTIAL/UNAVAILABLE 而非布尔，因为"跑了但没发现"与"没跑"是不同的观测事实 |
