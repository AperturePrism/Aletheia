## 5. 真实渠道实测（不是模拟）

本轮用自备密钥（`ark.cn-beijing.volces.com` / `deepseek-v4.1-flash`）实跑：

```bash
$ ALETHEIA_LLM_KEY=... pytest agents/tests/execution/test_live_planner.py -m llm_live -q
2 passed in 11.02s
```

输出（真实 Planner 产出）：

```
[live] 模型=deepseek-v4.1-flash 任务数=11 总预算=14848 实耗 tokens=2647
  - t1  [RECON]     确认授权范围与证据约束      deps=[]
  - t2  [RECON]     主动探测与 HTTP 指纹        deps=[t1]
  ...
  - t11 [REPORTER]  最小化报告导出              deps=[t10]
```

**密钥未入库**：验证方式是把密钥从**环境变量**读入、再与仓库内容比对
（不要把密钥字面量写进任何命令或文档 —— 见下方留痕）：

```bash
# 正确做法：密钥只存在于环境变量里，比对时也不落到命令行历史
[ -z "$ALETHEIA_LLM_KEY" ] || ! grep -rqF "$ALETHEIA_LLM_KEY" --exclude-dir=.git .
echo "exit=$?  # 0 = 未发现泄漏"
```

**★ 一处真实的自伤留痕（2026-11-03，已修复）**：本报告初稿在这一行写了
`grep -rn '<密钥前缀>' .` —— **把密钥的前 12 个字符写进了仓库文件**。
两个后果：

1. **密钥片段入库**（虽是前缀，仍属敏感材料）；
2. **那条断言自相矛盾**：grep 会命中它自己写下的那段模式串，
   于是"返回空"永远不成立 —— 若当时真去跑，会得到"有泄漏"而不知所措。

修法：改为从环境变量读取（上面的正确做法），并把字面量彻底移除。
**教训**：写"验证泄漏"的文档时，**该命令本身不能包含被验证的秘密** ——
否则验证工具自己变成了泄漏源。这正是 `07` §T8 的同一类问题：
真实敏感值的任何副本（哪怕是片段）都不该进入持久化介质。

### 6.4 门禁对迭代文档的覆盖机制（一处自我更正）

我最初在本节写下"`check-iteration-docs.sh` 的迭代列表硬编码到 I11，
因此缺 I12 文档不会被发现"。**这条是错的，我已核实并更正。**

实际机制（`scripts/check-iteration-docs.sh` 第 77 行）：

```bash
mapfile -t ids < <(grep -oE '^#### I[0-9]+ 实际达成情况' "$PLAN" | ...)
```

即**从 `docs/04` 里抽取已回填的迭代编号**，不是硬编码。补上
`#### I12 实际达成情况` 之后，本轮实测已覆盖 I12：

```
OK   I10 交接文档 + 自检报告齐全
OK   I11 交接文档 + 自检报告齐全
OK   I12 交接文档 + 自检报告齐全     ← 自动纳入
```

**更正后仍存在一个更窄的真缺口**：覆盖范围由"是否已有回填标题"驱动，
因此**尚未开始回填的迭代不会被检查**（例如 I13 现在不在检查范围内）。
这不影响正确性（没有回填就不该要求交付物），但意味着"门禁通过"不等于
"所有计划内的迭代都齐全"—— 它只保证"已宣称达成的迭代有交付物"。

**教训（写下来防止重犯）**：我基于"门禁输出里只看到 I9/I10/I11"就断言
脚本硬编码 —— 那只是 `tail` 截断造成的错觉。**断言脚本行为之前应当读脚本，
而不是从输出片段推断。**
