### ★ 由测试抓到的一个真实缺陷（不在 I10 范围，但由全量门禁暴露）

**`TestListOrdering` 间歇失败（`core/checkpoint`）。**

`List()` 用 `CreatedAt.Truncate(time.Second).Unix()` 排序，同秒时回退
到 ID。缺陷：三次快速 `Save` 若**跨越整秒边界**，秒级截断产生不同值
→ 走时间分支 → 顺序变成创建顺序而非 ID 顺序。

**实测约 1/6 概率失败**（20 次运行 3 次失败）。

**后果不止"测试不稳"**：`Latest()` 依赖本函数的顺序（取
`all[len-1]`）—— 顺序不确定意味着 **`Latest` 可能返回错误的检查点**，
那会让 `rewind` 恢复到非预期状态（04 §I6 DoD③ 的
"rewind 后证据一致"因此不可靠）。

修复：排序改为**完全按 ID**（P-5 要求完全确定）。ID 即创建顺序的
单调标识，因此与"按创建顺序"一致且不受时钟分辨率影响。

**验证**：修复后连续 20 次运行 **0 失败**。

### ★ 最重要的一条：当前检出数字的**性质**

我必须明确说明这一点，否则会被误读：

**当前 100% 的检出数字来自「模拟探测轮次」** —— 即测试直接构造了
带 `DATA_RETURNED` 的 `ProbeResult`，验证的是**判定逻辑与统计口径的
正确性**，**不是**对真实靶场的攻击能力。

要对外声称"检出能力"，必须补齐：
1. 可运行的靶场实例（docker compose）
2. 实际的探测执行（需 Sandbox 签发 exec_id）
3. 真实的端到端跑一轮

**在此之前不得对外宣称检出率。** 这一点必须写入任何对外材料，
与 M8 §3.2 N3（"不声称对黑盒无文档目标有通用能力"）和 §9
（"M8 给出的是可复现的下界，不是能力的上界"）同级。
