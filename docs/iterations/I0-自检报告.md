## 五、结论与下一步

### 5.1 复盘：CI 首跑七连败（本迭代最有价值的产出）

DoD② 达成，但过程是**连续 7 次 CI 失败**。这 7 次全部是本地验证覆盖不到的问题，
按 `docs/10` §0 的标准值得逐条记录 —— 它们暴露的是验证方法的盲区，不是运气问题。

| # | 失败现象 | 根因 | 性质 |
|---|---|---|---|
| 1 | `eslint: not found` + 大量 `TS2307 Cannot find module 'react-router-dom'` | `make env` 只装根 `package.json`（buf），**从没装 `web/` 的前端依赖** | 漏装 |
| 2 | 同上（修复未覆盖全部 job） | 修好了 `env`，但另一个 job 仍在自己 inline `npm install` | **流程性修复不彻底** |
| 3 | `make test-python ARGS=...` 用法报错 | CI 写 `ARGS=`，Makefile 定义的是 `PYTEST_ARGS=` | 变量名不匹配 |
| 4 | `uv: command not found` | `security-static` job 完全没有 setup 步骤；且 curl 装 uv 会装到 `~/.local/bin`（不在 runner PATH） | 漏步骤 |
| 5 | `Error 127: .venv/bin/python: No such file or directory` | Makefile 写死 venv 路径，而该 job 不跑 `make env` | 路径写死 |
| 6 | `Error 1: python3: No module named pytest` | 改成"按优先级回退"，但回退到 CI 的系统 python3 —— 它没装 pytest | **更健壮的回退反而更危险** |
| 7 | `Makefile:66: *** 未找到可用的 Python + pytest ... Stop.` —— **所有 6 job 全挂** | `PY = $(shell ...)` 在 Makefile **解析时**求值，而 `make env` 发生在 **recipe 执行时**。顺序错了 | **Make 硬约束** |
| 8 | Release 首跑：6 平台里 2 个 Windows 挂，`ParserError` 指向 `.ps1` | GitHub 的 `windows-latest` 默认 shell 是 **PowerShell**，而该 step 用 bash 语法。Linux/macOS runner 默认就是 bash，**所以只有 Windows 挂** | **平台默认值差异** |

**三条方法论教训**（比修复本身重要）：

1. **本地全绿 ≠ CI 能跑。** 7 次失败中没有任何一次能在本地复现 —— 本机 `.venv`
   一直存在、PATH 上的 `python` 恰好有 pytest、`web/node_modules` 早已装好。
   干净环境是唯一诚实的验证。这一条直接强化了 `docs/10` §0 的判断。
2. **"更健壮的回退"可能比明确的失败更危险。** 失败 #6 把显式的 127
   换成了隐密的 `No module named pytest` —— 前者一眼可知，后者会被误读成
   "测试在跑但没过"。真正要做的是**明确失败**，不是更聪明的降级。
3. **修复要打在结构上，不打在记忆里。** #1/#2 的根治方式不是"记得装 web 依赖"，
   而是让 `web-build` 依赖 `env-web` —— 之后任何调用方都不可能漏。

**固化措施**（防止同类问题再犯）：

- `.github/actions/setup` composite action：工具链setup 只有一处定义
- `tests/test_ci_workflows.py`（7 项）：断言每个 job 都调了统一 setup、
  workflow 里不含已废弃写法、CI 显式记录尚未自动化的门禁。
  **已变异验证**：删掉某 job 的 setup 步骤后测试确实 FAIL
- `scripts/py.sh`：Python 解析延到 recipe 内（规避 Make parse-time 陷阱），
  venv 缺失时自动创建而非报错
