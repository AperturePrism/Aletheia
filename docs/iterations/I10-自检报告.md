## 4. 自检的三个强制时点（`docs/10` §6）

### 时点 1：写完测试后、跑测试前 —— "这些断言真的在验证功能吗"

**★ 由测试抓到的两个真实缺陷：**

**缺陷 1：`UnboundLocalError`（`contract.py`）**

```python
for ctype, media in (body.get("content") or {}).items():
    ...
_ = ctype        # ← requestBody 缺席时该变量从未绑定
```

`GET` 请求通常没有 `requestBody` → 容器为空 → 循环体不执行 →
`ctype` 未绑定 → **运行时崩溃**。测试用真实形态的 OpenAPI
（含无 requestBody 的 GET）立刻抓到。

**缺陷 2：`TestListOrdering` 间歇失败（`core/checkpoint`，
不在 I10 范围但由全量门禁暴露）**

```
轮 1: all ok
轮 2: --- FAIL: TestListOrdering (0.03s) FAIL
轮 3: all ok
```

单独跑总是通过、全量跑偶尔失败 —— 典型的时序依赖。追查后确认：

`List()` 用 `CreatedAt.Truncate(time.Second).Unix()` 排序，同秒时回退
到 ID。**三次快速 Save 若跨越整秒边界**，秒级截断产生不同值 →
走时间分支 → 顺序变成创建顺序而非 ID 顺序。

实测 **1/6 概率失败**（20 次运行 3 次失败）。

**后果不止"测试不稳"**：`Latest()` 依赖本函数的顺序
（取 `all[len-1]`）—— 顺序不确定意味着 **`Latest` 可能返回错误的
检查点**，那会让 `rewind` 恢复到非预期状态（04 §I6 DoD③ 的
"rewind 后证据一致"因此不可靠）。

修复：排序改为**完全按 ID**（P-5 要求完全确定）。
**验证：修复后连续 20 次运行 0 失败。**

**`test_end_to_end_produces_reproducible_detection_numbers` 的断言强度：**
它跑 6 次并断言 `run() == first` —— 验证的是"检出数字**可复现**"
（M8 §6「可复现」测试要求原文："第三方在干净环境重跑得到同量级结果"），
而不只是"函数返回了东西"。

**`test_status_code_alone_is_not_enough` 的断言强度：**
它构造 `status_code=200, data_returned=False` 并断言判定返回 `None`。
这是 M8 §4.3 末句（"仅返回 200 状态码不足以判定"）的机械化守护 ——
若有人放松该门禁，测试立刻失败。

## 5. ★ 必须明确的诚实声明：当前检出数字的性质

**当前 100% 的检出数字来自「模拟探测轮次」** —— 测试直接构造了带
`DATA_RETURNED` 的 `ProbeResult`。

它验证的是**判定逻辑与统计口径的正确性**，
**不是**对真实靶场的攻击能力。

要对外声称"检出能力"，必须补齐：① 可运行靶场实例（docker）；
② 实际探测执行（Sandbox 签发 exec_id）；③ 真实端到端跑一轮。

**在此之前不得对外宣称检出率。** 这条与 M8 §3.2 N3
（"不声称对黑盒无文档目标有通用能力"）和 §9（"M8 给出的是可复现的
下界，不是能力的上界"）同级，已同时写入交接文档 §6。
